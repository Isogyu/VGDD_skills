# VGDD

VGDD は、AI エージェントの仕事を、人の統制の下に置くための基盤です。規則を起草する役割、作業する役割、独立して審査する役割を分けます。分けた境界は、プロンプトの約束ではなく、実行環境で強制します。

> **状態：新しい開発は終了しました（2026-11-15）。** 確かめたこと、先行研究との関係、得られた知見、残っている問題は、[終了報告](docs/final-report.md) にまとめています。このリポジトリは、記録として残します。残っている問題（終了報告の §7）を承知のうえで使ってください。

今は、ソフトウェア開発（Claude Code による開発）を対象にしています。開発のほかの業務へ広げることは、設計と試作の段階です。

## 考え方

| 役割 | 担うもの | できること |
|---|---|---|
| オーナー | 人 | 仕様の承認、統合の承認、裁定、停止と再開、規則の制定 |
| 立法 | AI | 規則と仕様の**起草**。効力は、オーナーの承認だけが与える |
| 行政 | AI | 票（仕事の単位）の起草、作業員の起動の申請、実装、統合の申請 |
| 司法 | AI（道具を持たない。別の系統のモデルを含む） | 差分と受け入れ条件と監査の結果だけを見て、判定を返す |
| Governance Kernel | スクリプトとフック | あらかじめ決めた権限と承認の条件を強制する。**判断はしない** |

Kernel が守る原則は次のとおりです。規範の正本は [`vgdd/kernel/SPEC.md`](vgdd/kernel/SPEC.md) です。

- **Kernel は LLM で可否を決めない。** 合否は司法が出す。Kernel は、その判定の扱い（統合する・しない）を機械的に決める。
- **境界は実行環境で強制する。** 権限の規則、フック、OS の sandbox、作業ツリーの隔離、別のプロセス、承認の記録を重ねる。
- **強制していない約束は、約束と書いて公開する。** 権限の表（[`vgdd/kernel/capabilities.json`](vgdd/kernel/capabilities.json)）に、権限ごとに、止める層と、確かめ方と、残る穴を書く。
- **承認は対象に結び付く。** 承認の後に仕様が 1 文字でも変われば、承認は効かない。
- **読めない・決められないときは、通さない。** 司法が使えないことは、合格ではない。
- **人が止められる。** オーナーは全体を止められる。再開の前に、記録と設定が変わっていないことを確かめる。
- **保証できないことを規範に書く。**（SPEC §12）

## 試す

要るものは、Node.js 22 以上、`git`、`jq`、UTF-8 のロケールです。確かめた環境は macOS だけです。

```sh
# 適合性テスト（Kernel の参照実装を、使い捨ての写しの上で試す。LLM は呼ばない。4〜6 分）
W=$(mktemp -d)
HOME="$W/home" VGDD_Z3_DIR="$W/home/tsubuyaki-z3" node vgdd/conformance/run.mjs

# 試作の試験と評価（依存パッケージなし）
node --test vgdd/next/test/*.test.mjs
node vgdd/next/bench/run.mjs
node vgdd/next/examples/walkthrough.mjs   # 試作の部品を 1 つの流れで通す見本
```

適合性テストの注意が 3 つあります。

- 上の例のように、ホームと保護領域の場所を、一時の場所に向けて実行してください。
- 同時に 2 つ動かさないでください（統合の関門の二重起動の防止が、互いを止めます）。
- このリポジトリには、配置済みの設定（`.claude/settings.json`）がありません。そのため、配置済みの設定を原本と比べる試験（ST16）と、それを参照する 1 件は合格しません。

## 確かめた範囲

「実装済み」と書くのは、適合性テストか、実際の運用の記録で確かめたものだけです。

| 確かめたこと | 方法 |
|---|---|
| 役割ごとに、止めるべき操作が止まり、通すべき操作が通る | 適合性テスト（このリポジトリの写しで実行できる） |
| 未承認の仕様の票は統合されない。承認の後に仕様を変えると、承認が効かない | 適合性テストと、実際の開発での運用の記録 |
| 司法が使えない状態は、合格にならない。判定が分かれたら、オーナーの裁定を待つ | 同上 |
| 全体の停止と、点検してからの再開 | 同上 |
| 規則の穴を、試験（判例）にして、前の版で落ちることを確かめてから直す | 規則の版ごとの履歴（[`vgdd/kernel/history.json`](vgdd/kernel/history.json)） |

**確かめていないこと**も書いておきます。

- 実際に稼働させたのは、1 つの案件、オーナー 1 人、macOS の機械 1 台、Claude Code の構成だけです。別の場所への構築と、ほかの人による導入は、通した記録がありません（[`docs/adoption.md`](docs/adoption.md)）。
- 関門があるのは、仕様の承認、実装、決定論的な監査、司法、統合、受け入れまでです。企画、設計、デプロイ、運用、廃止には、関門も記録もありません。
- 単一のエージェントとの比較や、仕事の成功率と費用の測定は、していません。
- 同じ機械の管理者は、記録を書き換えられます。外部への固定は、していません。
- フックの Bash の判定は、文字列の照合です。回避の余地があります（書き込みを最後に止めるのは、OS の sandbox です）。
- 司法の判定の正しさは、保証しません。別の系統のモデルが、同じ見落としをする可能性は残ります。

詳しくは、[`vgdd/kernel/SPEC.md`](vgdd/kernel/SPEC.md) の §12 と、[`docs/validation.md`](docs/validation.md) にあります。

## 次の段階の試作（`vgdd/next/`）

目標は、VGDD を「AI 駆動の開発の道具」から、「人の主権の下で、AI の組織を統治し、改善し続けるための基盤」へ進めることです。そのための部品を、稼働中の Kernel を変えずに、別の場所で先に作っています。

どの部品も、LLM を使わずに入力を検査します。検査に通っても、効力は生じません。

| 部品 | 何をするか |
|---|---|
| 権限の差分 | 権限の表の変更を「締める・影響しない・緩める・分類できない」に分ける。緩める変更は、AI の改善提案の通常の経路に乗せない |
| 改善提案の記録 | 提案、評価、審査、採用を別の主体に分ける。採用できるのは、人のオーナーだけ |
| 経験の記録 | 過去の指摘を、出どころつきの項目として持ち、作業員に引用として渡す。評価は、司法の結果からだけ更新する。司法には渡さない |
| 仕事のグラフと実行の状態 | 着手、申請、判定の取り込み、差し戻し、承認待ち、停止を、記録から作り直せる状態機械として持つ |
| 編成案の検査 | エージェントの編成を、承認済みの役割の型の範囲の中に限る。編成によって、新しい権限は生まれない |
| 追跡 | 要件から障害まで、成果物どうしのつながりを残してたどる |
| 外部への固定 | 記録の集まりの状態を 1 つの値にまとめ、後から書き換えを照合する（外部へ送る部分は作っていない） |
| 領域パック | 業務ごとの部分（仕事の単位、監査、司法の観点）を宣言に分ける。統治の核は弱められない |

**この試作で確かめたのは、検査の論理が、用意した攻撃の例に対して働くことまでです。** 稼働中の Kernel につないだときの強制、AI の仕事の質への効果、用意していない攻撃への耐性は、確かめていません。独立した審査を重ねるたびに抜け道が見つかったので、まだ残っていると考えています。

部品の説明、検証の結果、保証できないことは、[`vgdd/next/README.md`](vgdd/next/README.md) にあります。採用するには、規則の改正の手続き（起草、独立した審査、オーナーの承認）が要ります。

## 既知の制約

- 参照実装は、macOS、Claude Code、Git、Node.js の案件を前提にしています。
- 既定の置き場所と名前（保護領域 `~/tsubuyaki-z3`、票の置き場所 `docs/tasks/`、統合先のブランチ `main`、監査の `npm` のコマンド）は、開発のときの配置のままです。環境変数と引数で変えられるものと、まだ直書きのものがあります（[`docs/adoption.md`](docs/adoption.md)）。
- 先行研究との関係は、[`docs/research/prior-work.md`](docs/research/prior-work.md) に書いています。役割の分離、実行時の強制、権限の表からの試験の生成、規則の変更の分類には、それぞれ先行の研究か実装があります。VGDD の新しさは、検証すべき仮説として扱っています。
