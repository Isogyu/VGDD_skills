## 1. 用語

| 用語 | 意味 |
|---|---|
| オーナー（主権者） | 人。仕様の承認、統合の承認、裁定、停止、法律の制定を行う |
| 立法・行政・司法 | 規則を起草する役割、作業を実行する役割、独立して審査する役割。立法の効力はオーナーの承認だけが与える |
| Governance Kernel（Kernel） | あらかじめ決めた権限と承認の条件を、実行環境で強制する部品。判断はしない |
| 法律 | `vgdd/` 以下の規範・権限の表・フック・裁判所のスクリプト。変えられるのはオーナーだけ |
| 票 | 仕事の単位。受け入れ条件と、触ってよい範囲を持つ |
| 判例 | 適合性テストの1件。見つかった穴を再現する試験として足す |
| Z3 | 作業フォルダの外の保護領域。承認・判定・証拠の記録を置く。行政は読めず書けない |
| 試作（`vgdd/next/`） | 今回足した、起草段階の部品。稼働中の Kernel にはつないでいない |

## 2. 今の VGDD の分析

対象は Kernel p0.4.14 である。適合性テストは、この写しの上で 527 件のうち 525 件に合格した（2026-11-14）。合格しなかった 2 件は、配置済みの設定ファイルがこの写しにないことによる（[`vgdd/next/README.md`](../../vgdd/next/README.md) の基準の節）。

### 2.1 強み

1. **役割の境界を実行環境で強制している。** 権限ルール、フック、OS の sandbox、worktree の隔離、別プロセス、裁判所の検査、承認の記録の 7 層がある。約束だけで強制のないものは、権限の表に `promise` と書いて公開している（SPEC §1-3）。
2. **規範・参照実装・適合性テストが分かれている。** 権限の表（`capabilities.json`）から試験を生成するので、表と実装の食い違いは試験の不合格として現れる。
3. **止めるべき操作が止まることと、通すべき操作が通ることの両方を試している。** 新しい判例は前の版にかけて、新しい判例だけが落ちることを確かめる（試験が空回りしていないことの確認）。
4. **承認が対象に結び付いている。** 仕様の指紋、申請の SHA、法律の系統に結び付き、承認の後に1文字でも変われば効かない（INV-06）。
5. **失敗の扱いが fail-closed の側に倒してある。** 司法が使えないことは合格ではない。記録を読めなければ拒む。予算の利用量を読めなければ全量を使ったと数える。
6. **保証できないことを規範に書いている。** SPEC §12 に、文字列照合の限界や、同じ機械の管理者への無防備を列挙している。
7. **実運用の記録がある。** 題材のアプリの開発で、承認・差し戻し・裁定・停止と再開を実際に行った（[`docs/validation.md`](../validation.md)）。

### 2.2 弱み

| 分類 | 内容 |
|---|---|
| 適用の範囲 | macOS・Claude Code・Git・Node.js の案件・オーナー1人だけで確かめた。別の場所への構築と、ほかの人による導入は未確認（[`docs/adoption.md`](../adoption.md)） |
| 工程の範囲 | 関門があるのは、仕様の承認・実装・決定論的な監査・司法・統合・受け入れまで。企画、設計、デプロイ、運用、監視、障害対応、廃止には関門も記録もない |
| 構成 | エージェントの構成は静的（作業員、テスト担当、二系統の司法）。タスクに応じた選択はない（ADR-044 は「一部（静的）」） |
| 記憶 | 過去の作業の再利用は、同じ票の前の試行の記録だけ（`prior-record.mjs`）。票をまたぐ知識の共有はない（ADR-022 は後回し） |
| 自己改善 | 法律の改正は人の手続きで行っている。AI が改善を提案し、安全に採否を決める仕組みはない（ADR-021 は後回し） |
| 評価 | 適合性テストは「統治が働くか」を測る。単一エージェントとの比較や、仕事の成功率・費用の測定はしていない（ADR-013 は方針だけ） |
| 信頼の根 | 同じ機械の管理者は記録を書き換えられる。外部への固定はない |

### 2.3 技術的負債

参照実装を読んで見つけたもののうち、次の段階の妨げになるものを挙げる。行番号つきの一覧は [`vgdd/next/README.md`](../../vgdd/next/README.md) の付録にある。

1. **保護パスの定義が 5 か所に分かれている。** フックの2か所、裁判所、夜間の代行、設定ファイル、権限の表で、裁判所と夜間の代行では中身が違う。同期は人手である。
2. **鎖つきの記録が 2 系統あり、方式が違う。** 操作の証拠と予算の台帳で、ハッシュの取り方が違う。承認・裁定・夜間の合格の記録には鎖がない。
3. **裁判所の出来事の末尾は記録しているが、照合していない。** チェックポイントは裁判所の出来事の末尾も残すが、検証は操作の証拠だけを見ている。
4. **判定の記録の読み手が 5 か所にあり、ファイル名の規則と成立の印を各自が実装している。** 印の名前も、二つの司法で違う。
5. **裁判所が 1 つの大きな関数である。** 10 段階が直列に並び、途中の終了のたびに後始末を手で書いている。関数の単位では試験できない。
6. **元の案件の名前と配置が残っている。** 保護領域の名前がフックの正規表現に直書きされている。票の ID の形、`docs/tasks`、`main`、`npm` の4つの監査も直書きである。
7. **設定の渡し方がそろっていない。** リポジトリの場所を、引数で受けるスクリプトと環境変数で受けるスクリプトがある。

## 3. 研究課題：三権分立と、動的な編成・自己改善の両立

三権分立と Kernel は「権限をあらかじめ決めて動かさない」仕組みである。動的な編成と自己改善は「構成や規則を動かす」仕組みである。素直に足すと、動かす仕組みが決めた権限を崩す。チーフ AI が編成を決められるなら、司法のいない編成や、自分に都合のよい司法を選べる。AI が規則を改善できるなら、自分の権限を広げる改善を出せる。

この設計案の答えは次の7つの原則である。どれも、LLM に判断させずに機械で検査できる形にしてある。

**原則1　編成はデータで、権限は型である。** 動かしてよいのは「承認済みのどの役割の型を、何体、どの範囲で動かすか」までとする。役割の型が持つ権限と、数や予算の上限は法律であり、動かすには立法の手続きが要る。編成案は実行の前に機械が検査するデータで、検査に通っても効力は持たない。

**原則2　人の承認なしには、権限は広がる方向に動かない。** 委任、編成、領域パック、改善提案のどれを使っても、狭めることは自由にでき、広げることは人の承認なしにはできない。委任された子は親の範囲の部分集合だけを持つ（INV-03 の一般化）。法律を緩める変更は、機械が「緩める」と分類し、AI の改善提案の通常の経路から外す。

**原則3　提案・評価・審査・採用を別の主体にする。** 提案は誰が出してもよい（行政でも立法補佐でも）。評価は決定論的な試験が行う。審査は司法が行い、提案者と別の主体で、別の系統のモデルとする。採用はオーナーだけが行う。三権の分立を、自己改善の手続きにそのまま当てはめた形である。

**原則4　Kernel は判断しない。** 新しく足す検査（権限の差分、編成案、着手の組、領域パック）はすべて決定論的にする。LLM が関わるのは、提案の中身を書くことと、司法として審査することだけである（SPEC §1-1 を保つ）。

**原則5　検証する側は、足すことだけを通常の経路で認める。** 適合性テスト、評価のデータ、司法の定義への変更は、追加だけを通常の改善提案として受ける。削除と緩和は、法律を緩める変更と同じ扱いにする。評価される側が評価の物差しを縮める経路を塞ぐためである。

**原則6　経験は命令ではなく引用である。** 取り出した経験は、引用の囲みに入れたデータとして作業員に渡す。司法には渡さない。経験の評価（役に立ったか）は、作業員の自己申告ではなく、司法の結果からだけ更新する。

**原則7　既定は単一のエージェントである。** エージェントを増やすのは、仕事が並列に分けられ、範囲が重ならず、上限の中に収まるときだけとする。増やす理由は記録に残す。

### 3.1 チーフ AI と PM エージェントの位置

チーフ AI は、今の「行政の長」に当たる。PM エージェントは、行政の中で計画を担う役割として位置づける。どちらも行政に属し、次のことができる。

- 票の起草、仕事のグラフの案、編成案を**提案**する
- 承認された票について、作業員の起動を**申請**する
- 経験の候補と改善提案を出す

次のことはできない。これは今の Kernel がすでに強制しているか、試作の検査が拒む。

| できないこと | 止める仕組み |
|---|---|
| 司法を自分の配下に置く、自分で選ぶ | 編成案の検査（司法の型は委任されない）。稼働中の Kernel では、司法を起こすのは裁判所だけ |
| 人の承認を代行する役を編成に入れる | 編成案の検査（人の席は編成に入れられない） |
| 票の範囲や上限を広げる | 編成案の検査、着手の組の検査。稼働中の Kernel では仕様の指紋と予算の台帳 |
| 自分の改善提案を採用する | 改善提案の記録の検査（採用は人だけ） |
| 司法の審査を通さずに統合する | 稼働中の Kernel（統合できるのは裁判所と朝の承認だけ） |

### 3.2 共謀と、同じ誤りの連鎖

複数のエージェントが同じモデルの系統だと、同じ見落としを共有する。今の Kernel は、Claude の司法に Codex の司法を足して、これに備えている。試作では次を足した。

- 編成案に、行政のどの構成員とも系統の違う司法が1つ以上いることを求める
- 改善提案の審査者は、提案者と系統が違うことを求める
- 経験の評価を自己申告で増やせない

残る限界も書いておく。系統の名前は記録の上の申告で、機械が確かめたものではない。別の系統のモデルが同じ訓練データに由来する同じ見落としをする可能性は残る（SPEC §12 にすでにある）。エージェントどうしが成果物の中身を通じて示し合わせる経路は、文字列の検査では止めきれない。

## 4. 長期の全体アーキテクチャ

次の図は層の構成を示す。上の層が下の層を縛る。下の層は上の層を書き換えられない。

```
┌──────────────────────────────────────────────────────────────────────┐
│ 主権者（人）                                                          │
│   目標・仕様の承認／裁定／停止と再開／法律の制定／改善の採用          │
│   操作の窓口（Owner Console）：開始・承認・進捗・差し戻し・停止       │
└──────────────────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────────────┐
│ 統治の核（領域に依らない）                                            │
│   役割の型と権限の表 ／ 判定（フック）／ 承認の関門（指紋と記録）     │
│   司法の独立（入力の機械的な組み立て）／ 予算の台帳 ／ 証跡の鎖       │
│   停止と再開 ／ 適合性テスト ／ 不変条件                              │
│   ＋ 権限の差分 ／ 改善提案の記録 ／ 編成案の検査 ／ 経験の記録      │
└──────────────────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────────────┐
│ 汎用の実行（領域に依らない）                                          │
│   仕事のグラフ（依存・分岐・合流・承認待ち・差し戻し・再試行）        │
│   着手の組の選択 ／ 起動の窓口 ／ 長時間の実行と復旧                  │
└──────────────────────────────────────────────────────────────────────┘
┌───────────────────────────────┐  ┌──────────────────────────────────┐
│ 領域パック（業務ごと）         │  │ 接続（道具とデータ）              │
│   仕事の単位と成果物の形       │  │   開発エージェントの差し替え口    │
│   工程と関門 ／ 決定論的な監査 │  │   司法の CLI ／ MCP などの外部    │
│   司法の観点 ／ 保護する範囲   │  │   の道具（権限の表の対象にする）  │
└───────────────────────────────┘  └──────────────────────────────────┘
```

層を分ける線は次のとおりである。

- **統治の核**は、どの業務でも同じである。領域パックは統治の核を弱められない（司法を外せない、関門を消せない、役割と権限を定義できない）。この制約は、領域パックの検査が機械で確かめる。
- **汎用の実行**は、仕事を節、依存を辺とするグラフを扱う。節の中身が開発の票か、調査の課題かを知らない。
- **領域パック**は宣言である。開発なら「成果物は Git の木、統合は fast-forward、監査は試験と型検査と lint」と書く。
- **接続**は、外の道具とデータの口である。外から来た文字列は命令として扱わない。外の道具の呼び出しも、権限の表とフックの対象にする。

### 4.1 今の実装との対応

今の参照実装は、4 つの層が 1 つにまとまっている。どの部分がどの層に当たるかを次に示す。

| 層 | 今の実装で当たる部分 | 分けるときの作業 |
|---|---|---|
| 統治の核 | フックの判定の枠、仕様の指紋と承認、予算の台帳、証跡の鎖、停止と再開、司法の入力の組み立てと出力の検証、Owner Console の安全の作り | 鎖つき記録の統一、保護パスの定義の一元化、判定の記録の読み手の統一 |
| 汎用の実行 | 夜間の代行の「試行、差し戻し、前の記録を渡す」の繰り返し、起動の窓口、統合キュー | 票の依存をグラフとして扱う。`T-NNN` と `docs/tasks` を設定に出す |
| 領域パック | 裁判所の段階 3（差分の範囲）と段階 5（`npm` の監査）、票の節の見出し、作業員への指示の文面 | 監査のコマンドと成果物の形を宣言に出す |
| 接続 | Claude Code のフックの入力の形、`claude` と `codex` の CLI の呼び出し | 開発エージェントと司法の差し替え口（ADR-023） |

## 5. 5 つの基盤

指示にあった 5 つの候補について、長期の姿、今回の試作、まだないものを分けて書く。試作の API、ガード、試験の結果は [`vgdd/next/README.md`](../../vgdd/next/README.md) にある。

### 5.1 グラフ型の実行基盤

**長期の姿。** 仕事の依存、分岐、合流、並列、差し戻し、承認待ち、再試行、長時間の実行、障害からの復旧を、1 つのグラフの状態として扱う。状態は追記専用の記録から作り直せる（予算の台帳と同じ作り）。

**今あるもの。** 票の `depends_on`、統合キュー（前の票が止まっても後ろは止まらない）、差し戻しの上限、起動の窓口の状態の記録。

**今回の試作（`taskgraph.mjs`）。** 票の集まりを DAG として読み、循環と存在しない依存を拒む。着手してよい節と、着手できない理由を返す。同時に動かしてよい組を、範囲の重なりと上限を見て選ぶ。未承認の節や止まった節が、それに依存しない節を妨げないこと（INV-12）を試験で示した。構成の勧め（単一、並列、段ごと）は理由つきで返す。

**試作の追加（`runstate.mjs`）。** 着手、申請、判定の取り込み、差し戻し、承認待ち、夜間の保留、停止を、追記専用の記録の上の状態機械として取り出した。記録から状態を作り直せるので、途中で落ちても続きから再開できる。誰のどの出来事なら状態を移してよいかを機械的に検査するだけで、合否は外から来る司法の判定が決める。設定（上限、同時の数、必須の審査）は、記録の中のオーナーの出来事として固定する。

**まだないもの。** この状態機械を動かす常駐の実行器。今の夜間の代行と裁判所へのつなぎ。条件つきの分岐。LangGraph のチェックポイントや Temporal の耐久実行に当たる部分は、自前の追記専用の記録で試作したが、既存の実装と比べてはいない。

### 5.2 知識・経験の管理基盤

**長期の姿。** 実行の履歴、判定の指摘、設計の決定（ADR）、障害の記録を、出どころつきの項目として持ち、必要な場面で取り出す。字句、意味（埋め込み）、関係（グラフ）の 3 つの検索を、差し替えられる口の後ろに置く。

**今あるもの。** 同じ票の前の試行の記録。根拠のある指摘と未検証の仮説を分け、伏せ字にして、引用の囲みで作業員にだけ渡す。

**今回の試作（`experience.mjs`）。** 項目を「1 つの出来事から得た反省」と「複数の票から帰納した経験」の 2 層に分けた。生の記録は写さず、証拠への参照だけを持つ。出どころのない項目は作れない。信頼の度合いは出どころの種類から機械が決める。昇格はオーナーだけが行う。役に立ったかのカウンタは、裁判所の側のプロセスが司法の結果からだけ更新する。司法の役割には渡さない。更新は項目の単位の追加だけで、全体の書き換えという操作がない。

**まだないもの。** 意味検索。試作の検索は字句の一致で、埋め込みは使っていない（差し替えの口だけある）。グラフ検索、ADR と障害記録の取り込み、判定の記録から反省の候補を自動で作る処理、稼働中の Kernel へのつなぎ。経験を渡すと仕事の成功率が上がるかは測っていない。

### 5.3 適応型のマルチエージェント

**長期の姿。** 仕事のグラフの形と危険の度合いから、構成を選ぶ。選ぶのは承認済みの型の中からで、選んだ理由を記録する。不要なエージェントは起こさない。

**今あるもの。** 静的な構成。並行は、既定が 1 で、オーナーがキューで明示したときだけ増える。

**今回の試作（`team.mjs`、`taskgraph.mjs` の勧め）。** 編成案を検査する。型の実在、範囲は狭めるだけ、委任の単調性、権力の兼任の禁止、司法の確保と系統の違い、人の席の不可侵、上限の順守を見る。構成の勧めは、既定を単一とし、並列は条件がそろうときだけにした。

**根拠にした研究。** Google Research ほかの研究（arXiv 2512.08296）は、逐次の依存が強い仕事では複数エージェントの構成がすべて単一より悪く、検証のない独立の並列が誤りを最も増幅すると報告している。AdaptOrch（arXiv 2602.16873）はグラフの指標で構成を選ぶが、計算量をそろえた比較では構成に固有の効果は小さい。そこで、指標による積極的な切り替えは採らず、「既定は単一、並列は条件つき」という保守的な規則にした。閾値は VGDD の仕事で校正していない。

**まだないもの。** 起動の窓口へのつなぎ。構成ごとの成功率と費用の実測。モデルの能力の評価に基づく型の選択（ADR-045）。

### 5.4 統治された自己改善

**長期の姿。** AI が、手順、プロンプト、編成の型、知識の管理、評価の方法の改善を提案する。提案は、決定論的な評価と独立した審査を経て、オーナーが採用する。採用した変更は取り消せる。

**今あるもの。** 法律の改正の手続き（起草、憲法審査、オーナーの承認）。穴を判例にして、前の版で落ちることを確かめる運用。

**今回の試作（`authority-delta.mjs`、`improvement.mjs`）。**

- **権限の差分。** 権限の表の旧版と新版を比べ、変更を「締める」「影響しない」「緩める」「分類できない」に分ける。許可の追加、強制の層の削除、確かめ方の削除、不変条件の格下げは「緩める」になる。分類できない変更は「緩める」と同じ扱いにする。
- **改善提案の記録。** 提案、評価、審査、採用、取り消しを、鎖つきの記録の上の状態の移り変わりとして持つ。採用できるのは人だけ。提案者、評価者、審査者は別の主体。評価と審査と採用は提案の指紋に結び付き、評価の後に中身を変えると効かない。試験の合格が減る変更、試験そのものを減らす変更は採用できない。法律を緩める提案は、憲法審査を経ていなければ採用できない。

**この試作が変えないこと。** 法律の変更は、今までどおり起草、憲法審査、オーナーの承認を経る（ADR-011）。権限の差分は、この手続きを軽くしない。足すのは、AI が出した提案に対する機械的な下限と、オーナーが見る要約である。

**まだないもの。** 稼働中の Kernel へのつなぎ（行政が提案を置く窓口、保護領域への取り込み、Owner Console の画面）。採用した変更を実際に配置する処理と、取り消しの実行。プロンプトや手順の改善が仕事の質を上げるかの測定。権限の表に現れない変更（フックの正規表現の書き換えなど）の分類。

### 5.5 評価・実験の基盤

**長期の姿。** 複数の構成を同じ条件で比べ、成功率、品質、安全性、時間、費用、人の介入の回数、障害からの復旧を測る。変更の前後を比べ、要素を 1 つずつ外して効果を分ける。

**今あるもの。** 適合性テスト（統治が働くかの試験）。前の版との比較。

**今回の試作（`bench/run.mjs`）。** 試作の検査について、攻撃の例がすべて止まること、良性の例がすべて通ること、検査を 1 つ外したときにどの攻撃が通るかを測る。鎖つき記録と経験の取り出しの所要時間も測る。

**測っていないもの。** LLM を使う比較実験。Phase 1 の仕様書（[`vgdd-phase1-spec-v0.1.md`](vgdd-phase1-spec-v0.1.md) §9）の、単一エージェントとの比較と罠のタスクは未実施である。これには API の費用とオーナーの承認が要る。先行研究の調査（Artificial Intelligence Review の総説）は、既存のベンチマーク 15 件のうち安全性と費用を採点に含むものがないと指摘している。VGDD の評価では、成功率に加えて、止めるべき操作の阻止率、差し戻しの回数、人の介入の回数、1 件の成功あたりの費用を測る計画とする。

## 6. 開発ライフサイクル全体への対応

次の表は、工程ごとの成果物、関門、今の状態を示す。「関門」は、その工程の成果物を確定させる前に通す承認か審査である。

| 工程 | 成果物 | 関門（案） | 今の状態 |
|---|---|---|---|
| 企画・構想 | 目標と範囲の文書 | オーナーの承認 | 関門なし。Kernel の外で人が行う |
| 要求分析・要件定義 | 要件（ID つき） | オーナーの承認 | 一部。要件の行は仕様の指紋に入る。要件そのものの審査はない |
| 基本設計・詳細設計 | 設計の文書、決定の記録 | 司法の審査とオーナーの承認 | 関門なし。票の「手順の案」は仕様の外 |
| 実装 | 差分 | 決定論的な監査と二系統の司法 | **実装済み**（裁判所） |
| 単体・結合の試験 | 試験と結果 | 決定論的な監査 | **実装済み**（`npm` の 3 つの監査に限る） |
| システム・受け入れの試験 | 動作の確認 | オーナーの受け入れ | 一部。受け入れは申告の記録で、確かめた中身は保証しない |
| セキュリティ検証 | 審査の結果 | 別系統の司法 | 一部。指定した票と依存の変更のときだけ |
| リリース・デプロイ | 統合と配置 | オーナーの承認 | 統合までは**実装済み**（朝の承認）。デプロイは対象外 |
| 運用・監視・障害対応 | 出来事と対応の記録 | 重大度に応じた停止と復旧 | Kernel 自身の停止と再開だけ。アプリの運用は対象外 |
| 保守・改修・継続的改善 | 票、改善提案 | 仕様の承認、改善の採用 | 票は実装済み。改善提案は試作 |
| 廃止・移行 | 廃止の計画、データの移行 | オーナーの承認 | 関門なし |

### 6.1 追跡

要求から運用上の問題まで、成果物をたどれるようにする。今の記録には、次のつながりがすでにある。

```
要件の ID ── 票 ── 仕様の指紋 ── 承認の記録 ── 申請の SHA ── 判定の記録 ── 統合のコミット ── 受け入れの記録
```

欠けているのは、両端である。企画と設計の成果物は記録の外にある。統合の後の出来事（障害、利用者の指摘）から票へ戻るつながりもない。

**設計と試作（`trace.mjs`）。** 成果物どうしのつながりを、1 種類の記録（追跡の記録）として持つ。1 行が「どの成果物が、どの成果物に、どの関係（満たす、導く、検証する、起因する など）でつながるか」を表す。書くのは裁判所の側のプロセスと人のオーナーで、行政は書けない。この記録から、要件ごとに「どの票が満たし、どの判定が検証し、どの障害が起因したか」を作り直せる。今の Kernel の記録（承認、夜間の合格、判定、裁定、受け入れ）からつながりを作る取り込みも試作した。**稼働中の Kernel にはつないでいない。企画と設計の成果物、障害の記録を実際に入れる運用も、まだない。**

### 6.2 段階の計画

| 段階 | 内容 | 終わりの条件 | 要る承認 |
|---|---|---|---|
| A（今回） | 調査、設計案、`vgdd/next/` の試作と試験 | 試験が合格し、基準の適合性テストが変わらない | なし（法律を変えていない） |
| B | 試作を稼働中の Kernel につなぐ法律の改正案。提案の窓口、保護領域の記録、裁判所からの経験の評価、起動の窓口での編成案の検査、新しい不変条件と判例 | 新しい判例が前の版で落ち、新しい版で通る | 憲法審査とオーナーの承認 |
| C | 技術的負債の解消（§2.3）と、別の場所への構築の検証（[`docs/adoption.md`](../adoption.md) の場面 B） | 別のフォルダと別の保護領域で、票が 1 枚最後まで通る | 法律の改正としてオーナーの承認 |
| D | 比較実験（単一エージェントとの比較、罠のタスク、構成のアブレーション） | 事前に決めた合格と撤退の条件で判定する | 費用の承認 |
| E | 工程の拡張（設計の関門、追跡の記録、デプロイと運用の出来事の取り込み） | 設計から受け入れまでを 1 件たどれる | 法律の改正としてオーナーの承認 |
| F | 開発以外の領域パックで、仕事を 1 件通す | 承認、審査、確定、記録が通る | 領域パックの採用の承認 |

段階 C を B の前に行う案もある。負債を残したままつなぐと、保護パスの定義がさらに増えるためである。順番はオーナーの判断とする。

## 7. システム開発以外への汎用化

### 7.1 分ける線

指示にあった 6 つの要素と、設計上の置き場所の対応は次のとおりである。

| 要素 | 置き場所 | 領域に依るか |
|---|---|---|
| 共通の統治機構 | 統治の核 | 依らない |
| 汎用タスク実行機構 | 汎用の実行 | 依らない |
| エージェントの役割・権限 | 統治の核（役割の型と権限の表） | 型は依らない。型の具体的な範囲は票が決める |
| 業務固有のワークフロー | 領域パック（工程と関門） | 依る |
| 業務固有の評価・審査基準 | 領域パック（監査と司法の観点） | 依る |
| 外部ツール・データとの接続 | 接続 | 道具に依る |

### 7.2 領域が変わると変わるもの、変わらないもの

| | 開発 | 調査報告（例） | 変わらないこと |
|---|---|---|---|
| 仕事の単位 | 票 | 調査の課題 | 受け入れ条件と範囲を持ち、指紋を承認する |
| 成果物 | Git の差分 | 文書と出典の一覧 | 承認した範囲の外に及べば確定しない |
| 決定論的な監査 | 試験、型検査、lint | 出典の形式、字数、禁止語 | 不合格は LLM の合格で取り消せない |
| 司法の観点 | 要件、正しさ、安全性、試験 | 根拠、出典との一致、論理 | 行政の説明を入力に入れない。道具を持たない |
| 確定 | main への統合 | 公開用の場所への写し | 確定できるのは裁判所と人の承認だけ |

### 7.3 今回の試作（`domain.mjs`）

領域パックの宣言の形と、その検査を作った。検査は、領域パックが統治の核を弱めていないことを見る。司法を無効にできない。行政の説明を司法の入力に入れられない。関門をすべて消せない。統治の核のパスを保護から外せない。役割、権限、予算、停止を定義できない。

例を 2 つ置いた。`software-dev.json` は、今の実装が前提にしていることを書き写したものである。`research-report.json` は開発以外の例である。**後者で実際に仕事を回したことはなく、監査のコマンドは実在しない例である。** 汎用化が成り立つかは、段階 F で 1 件通すまで分からない。

### 7.4 汎用化の難所

開発以外では、次の点が開発より難しい。設計の段階で分かっているものを書いておく。

1. **決定論的な監査が弱い。** 開発には試験と型検査がある。文書や分析には、機械で確かめられる性質が少ない。司法（LLM）への依存が増え、判定の誤りの影響が大きくなる。領域パックは、決定論的な監査がない場合にその旨の公開を必須にしている。
2. **成果物の範囲を切りにくい。** `files_allowed` のように、触ってよい範囲を前もって列挙できない仕事がある。
3. **確定を取り消しにくい。** 外に送った文書や、行った契約は戻せない。確定の前の人の承認を、開発より重くする必要がある。
4. **外の情報への依存が大きい。** 調査は検索結果を読む。読んだ内容を命令として扱わない仕組みを、接続の層で強制する必要がある。今の Kernel にこの強制はない。

## 9. 利用者に見せるもの

内部の構造が増えても、オーナーの操作は増やさない。今の Owner Console の操作（承認、開始、統合、停止、再開、受け入れ、裁定）に、次の 3 つを足す案である。どれも未実装である。

- **改善の受け箱。** 改善提案を、権限の差分の分類（締める、緩める）と、評価と審査の結果つきで並べる。操作は採用と却下だけ。緩める提案は別の欄に分け、憲法審査の結果がなければ採用の操作を出さない。
- **経験の受け箱。** 昇格の候補を、出どころの数と評価つきで並べる。命令らしい文を含む候補には警告を付ける。
- **編成の表示。** 票ごとに、今の編成と、その構成を選んだ理由を出す。

承認待ちが増えすぎないよう、1 つの AI が出せる未決の提案の数に上限を置いた（試作）。まとめて見せる、優先順位を付ける、という部分（ADR-039）は未着手である。

### 10.1 未実装の事項

### 10.2 技術的なリスク

| リスク | 内容 | 備え |
|---|---|---|
| Kernel の肥大 | 「最初に作るのは小さな Kernel」という方針と、機能の追加がぶつかる | 試作を核と分け、採用は部品ごとにオーナーが決める。採用しない選択を残す |
| 行為者の申告 | 試作の記録は、行為者（役割、種類、系統）を呼び出し側の申告で受ける | 保護領域に置き、オーナー側のプロセスだけが書く配置で強制する。配線するまでは保証しない |
| 承認の疲れ | 提案と経験の候補が増えると、オーナーが中身を見ずに承認する | 未決の数の上限。分類と評価の要約。緩める提案を分けて見せる |
| 評価のすり抜け | 提案が、試験に通るが実害のある変更を出す | 審査を別系統の司法にする。採用は人。取り消しの記録。試験にない害は止められない |
| 分類の漏れ | 権限の差分は権限の表だけを見る。フックや裁判所のスクリプトの変更は見ない | 表に現れない法律の変更は、今までどおり全部を憲法審査に回す |
| 見つかっていない抜け道 | 独立した審査を 2 回行い、1 回目に 29 件、2 回目に 11 件の発見があった。発見が続いたので、まだ残っていると考えるべきである | つなぐ前に、別の系統のモデルと人による審査を重ねる。発見は判例にして残す |
| 経験の汚染 | 誤った経験や、命令を含む経験が入る | 出どころの必須、候補の固定、オーナーの昇格、引用の囲み。文字列の検査は完全ではない |
| 閾値の根拠 | 構成の勧めの規則は、VGDD の仕事で校正していない | 既定を単一にし、勧めは理由つきの参考にとどめる |
| 記録の増加 | 鎖つき記録は、追記のたびに全行を確かめる | 件数に対する所要時間を測った。大きくなれば、チェックポイントで区切る設計が要る |

### 10.3 今後の研究課題

検証すべき仮説として書く。どれもまだ確かめていない。

1. **統治の費用と効果。** 権限の制御と独立した審査を足すと、成功率、残る欠陥、罠の阻止率、1 件の成功あたりの費用はどう変わるか（Phase 1 の仕様書 §9 の実験）。
2. **経験の効果。** 司法の結果からだけ評価を更新する経験の記録は、自己申告で更新する方式と比べて、誤った経験の残り方と仕事の成功率がどう違うか。
3. **構成の選択。** 「既定は単一、並列は条件つき」の規則は、グラフの指標で切り替える方式と比べて、成功率と費用がどう違うか。
4. **権限の差分の完全性。** 権限の表の変更のうち、機械の分類が人の判断と食い違う割合はどれだけか。過去の改正 15 回に当てた結果は [`vgdd/next/README.md`](../../vgdd/next/README.md) §4.5 にある。15 回のうち 4 回は、権限の表に現れないスクリプトの改正で、差分には出なかった。複数の人の判断との突き合わせはしていない。
5. **別系統の司法の独立性。** 二つの系統の司法が同じ見落としをする割合はどれだけか。今の判定の記録（判定が分かれた件数）から測れる。
6. **領域の転用。** 決定論的な監査が弱い領域で、統治の核はどこまで効くか。
7. **人の負担。** 承認、裁定、受け入れに、オーナーは 1 件あたりどれだけ時間を使うか。提案が増えたときに承認の質が保たれるか。
