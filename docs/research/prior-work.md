## 1. この文書の範囲と読み方

### 1.1 VGDD とは何か

VGDD は、AI エージェントを人の統制の下に置く開発ガバナンス基盤です。ガバナンスとは、誰が何をしてよいかを決め、その決まりを守らせる仕組みのことです。

VGDD は二つの考え方でできています。

一つ目は三権分立です。立法は規則の起草と、人による承認を指します。行政は実際の作業を指します。司法は独立した審査を指します。VGDD では、人（オーナー、つまり主権者）が立法の効力と最終の承認を持ちます。AI は起草までしかできません。

二つ目は Governance Kernel（以下、Kernel）です。Kernel は、あらかじめ決めた権限と承認の条件を、プロンプトではなく実行環境で強制する部分です。Kernel は LLM（大規模言語モデル）で可否を決めません。可否の判定は司法が出し、Kernel はその判定の扱い（統合する、しない）を機械的に決めるだけです。

今の実稼働の記録は、macOS、Claude Code、Git、Node.js、オーナー1人の構成だけにあります。ほかの構成では確かめていません。

### 2.1 Self-Improvements in Modern Agentic Systems: A Survey

#### 書誌と査読の状況

- arXiv 2607.13104。著者は Zhe Ren、Yimeng Chen、Dandan Guo ほか（Mingchen Zhuge、Jürgen Schmidhuber を含む12名）。責任著者は Yimeng Chen と Dandan Guo。
- 所属は吉林大学 AI 学院、KAUST、アルバータ大学、IDSIA/USI/SUPSI、独立研究者です。
- 投稿は 2026-07-14 で、v1 のみです。cs.AI。97ページ、図12。
- 査読や採択の記載は、抄録ページにも本文にもありません。査読状況は不明です。投稿から日が浅い論文です。
- 水準：本文確認（テキスト抽出）。ただし97ページの全文精査はしていません。

#### 中心の枠組み

論文は、エージェントを二つの部分の組として定義します。基盤モデルのパラメータ θ と、その外側の足場（scaffold）Σ です。Σ は、プロンプト、記憶、ツール、制御ロジックからなります。

自己改善とは、エージェント自身が学習信号（実行の軌跡、批評、検証結果、編集案）を作り、更新の手続きで恒久的な変更を確定することです。経路は二つに分かれます。

1. 基盤モデルの改善。θ を更新し、Σ は固定します。遅いが安定です。分布の変化や、以前の学習を忘れる問題を抱えます。
2. 足場の改善。Σ を更新し、θ は固定します。速く、取り消せます。ただし、記憶の汚染（memory poisoning）や、ツールの意味のずれが起きます。

#### 検証と採用の条件（VGDD に最も関係する部分）

論文の 9.1 節は、設計上の含意を次のように述べます。

- 評価者（critic）は、統治の対象となる基盤です。閉じた改善の輪の中の critic は攻撃を受ける面です。改善の能力の上限は、critic が悪用に耐えられるかで決まります。
- 改善を提案する役と、採否を決める役を混同すると、自分で自分を確認する輪に崩れます。critic は生成する側から切り離すべきです。
- critic 自体を進化させる場合も、評価される側の無制約な制御下に置きません。変更が単調（たとえば、テストを足すだけ）のときに限り、人間の監査記録を見て通します。
- 自己改善するエージェントは、「保護された実行環境で動く、信頼できないコード」と見なします。
- 構造の更新を確定する前に、検証器が、機能の正しさ、ツール権限の境界、状態の揺れへの頑健性を確かめる、層状の関門（ゲート）を置きます。
- 一時的な攻撃（一度だけのプロンプトインジェクション）が、汚染された記憶として確定すると、恒久的な弱点になります。

8.1 節は、平均の成功率だけでなく、回帰率（前に通ったものが落ちる割合）、まれな大きい失敗の指標、安全ポリシー違反を、反復ごとに追うよう勧めます。人間の介入の量も報告項目に入れます。

#### 実験条件と主な数値

この論文はサーベイであり、独自の実験はありません。数値による結果は、材料では抽出されていません。

#### 限界

- 著者の述べる限界：完全に開かれた再帰的自己改善は、まだ大きな課題です。今の実現は、人間が設計した目的と安全の手順の内側の、範囲が決まった検証可能な輪です。
- こちらから見える限界：層状ゲートなどの安全設計は、主張として書かれているだけで、実装や測定の裏づけは確認できていません。個々の引用の質は検証していません。

#### 再現性、コード、ライセンス

論文のライセンスは、arXiv の非独占配布ライセンスです。本文に GitHub と Project Page の表示がありますが、URL とライセンスは確認できていません。

#### VGDD への適合の判断

採用する考え方は次のとおりです。

- 提案する主体と、採否を決める検証器を分ける原則です。VGDD の三権分立の配置（AI は起草、人が効力を与える）と同じ方向にあります。
- 検証器やテストの変更は、追加だけの単調な変更に限り、人間が記録を見て通すという条件です。VGDD の適合性テストは、判例（新しい試験）を足す形で増えており、考え方が近いです。
- 更新の履歴を保ち、取り消せるようにすることです。
- 回帰率の追跡を採用の条件に含めることです。

採用しない考え方は、全面的な自己参照のコード書き換え（Gödel Machine 系）です。人が主権者であるという VGDD の前提と合いません。

理由と注意：この論文は、VGDD が先に実装している考え方を、規範的な主張として整理している位置にあります。VGDD の側に、論文の主張を実証した記録があるわけではありません。逆に、論文の主張が VGDD の設計を実証したとも言えません。

### 2.2 From Storage to Experience

#### 書誌と査読の状況

- arXiv 2605.06716。著者は Jinghao Luo（華南師範大学）、Yuchen Tian（香港バプテスト大学、プロジェクトリーダー）ほか9名で、責任著者は Jing Ma です。
- 投稿は 2026-05-07 で v1 のみです。cs.AI と cs.CL。
- ACL 2026 Findings に採択と記載されています。
- 水準：要約モデル経由の取得です。約18万字のうち、後半の一部だけを精読しています。

#### 中心の枠組み

エージェントの記憶を、過去の軌跡（観測と行動の記録）をどれだけ変換するかで、三つの段階に整理します。段階は置き換えではなく、併存できます。

1. 保存（Storage）：軌跡をほぼそのまま保ちます。線形、ベクトル（意味検索）、構造化（データベースや階層）があります。
2. 反省（Reflection）：完了した軌跡を分析し、批評や修正を含む独立した記憶の単位を作ります。
3. 経験（Experience）：複数の軌跡をまとめ、少数の一般的な規則やスキルを導きます。明示的（自然言語の方策、実行できるスキル）、暗黙的（重みへの内部化）、両方を組み合わせた形があります。

ここでの「意味検索」とは、単語の一致ではなく、意味の近さで関連する記憶を探す方法です。

#### 実験条件と主な数値

サーベイであり、独自の実験はありません。著者は、段階ごとに目的、モデル、環境が違うため、数値による比較はしないと明記しています。

#### 限界

- 著者の述べる限界：数値の比較がないこと、新しい学習の枠組みではないこと、経験の段階は2025年末以降の新しい領域で未査読のプレプリントを含むこと、既存のベンチマークは保存と検索の評価が中心で、抽象化と汎化の評価が著しく不足していること。
- こちらから見える限界：調査担当は、読めた範囲で、安全性、ガバナンス、記憶の汚染への言及を見つけていません。誰が記憶を書き換える権限を持つかは扱われていません。ただし、未読の部分があるため、「言及がない」とまでは言えません。

#### 再現性、コード、ライセンス

コードはありません（サーベイ）。

#### VGDD への適合の判断

採用する考え方は次のとおりです。

- 作業の履歴を、保存、反省、経験の三つの層に分けて考えること。生の記録は変えられない証拠として残し、反省と経験は、出典の軌跡への結びつきを必須にした別の記録にします。
- 経験（規則やスキル）への格上げは、複数の軌跡の裏づけと、人の承認を条件にし、自動では行わないこと。
- 規則に有効期限や再検証の条件を持たせること。
- 保存の無制限の増加は誤りの広がる元になるので、削除と失効も審査の対象にすること。

採用しない考え方は、暗黙の経験（重みへの内部化）です。人が中身を検査も撤回もできず、Kernel で強制することが難しいからです。明示的な自然言語の規則と、実行できるスキルに限るのが妥当です。

注意：VGDD の今の実装は、この枠組みの保存の層（証拠ストア）と、最小の反省の層（前の試行の記録。第3節と第4節を参照）にあたります。経験の層はありません。上の「採用する考え方」は、将来の拡張の設計の指針であり、実装済みではありません。

### 2.3 AdaptOrch

#### 書誌と査読の状況

- arXiv 2602.16873。著者は Geunbin Yu の単著で、所属はページに記載がありません。
- 投稿は 2026-02-18 で v1 のみ、21ページです。cs.MA と cs.AI。論文のライセンスは CC BY 4.0 です。
- 査読と採択の記載はなく、プレプリントです。
- 水準：要約モデル経由の取得です。

#### 中心の枠組み

主張は、モデルの性能が近づいてくると、どのモデルを選ぶかよりも、複数のエージェントをどうつなぐか（オーケストレーションのトポロジ）の影響が大きくなる、というものです。

タスクを、依存関係の有向グラフ（DAG。向きのある、輪のないグラフ）として表します。三つの指標を使います。並列の幅 ω（同時に進められる最大の数）、最長の経路の深さ δ、結合の密さ γ（依存の強さの平均）です。トポロジは、並列、逐次、階層、混合の4種です。

選び方は、LLM を呼ばない決定的な規則です。依存の辺がなければ並列、幅が1なら逐次、結合が強く規模が大きければ階層、幅の割合が大きく結合が弱ければ並列、それ以外は混合とします。結果の合成では、埋め込みの類似度による整合スコアを使い、低ければ調停役を呼び、再度の振り分けをします。

#### 実験条件と主な数値

- モデルは GPT-4o-mini、Claude 3.5 Haiku、Gemini 2.0 Flash、Llama 3.3 70B、Qwen 2.5 72B です。
- ベンチマークは SWE-bench Verified（500件）、GPQA Diamond（198件）、HotpotQA（500件）です。閾値は15%の開発用データで調整し、残り85%で評価しています。seed は 42、温度は 0、3回の実行で標準偏差は 0.8% 未満です。
- 最良の単一モデルから AdaptOrch への変化は、SWE-bench が 42.8 から 52.6、GPQA が 46.2 から 53.1、HotpotQA が 68.3 から 76.4 です。見出しの「12〜23%」は相対の改善で、絶対では 6.9 から 9.8 点です。
- 計算量を揃えた Self-MoA（同じモデルを複数回呼んで混ぜる手法）は、51.5、52.3、75.5 でした。AdaptOrch の改善の89%は、Self-MoA で再現できます。トポロジを考慮したことに固有の寄与は、残りの11%です。
- SWE-bench のアブレーション（部品を外す実験）では、固定の混合トポロジが 49.8 で、AdaptOrch の完全版は 52.6 でした。トポロジ選択だけの効果は 2.8 点ほどです。「分解なし」は、最良の単一モデルと同じ 42.8 です。

#### 限界

- 著者の述べる限界：分解の質が分解を行うモデルに依存すること、結合の4段階が粗いこと、並列実行が API の速度制限と予算に当たること、ベンチマークが3種だけであること。
- こちらから見える限界：単著で未査読です。使われているのは2024年から2025年の小型のモデルです。本文に不整合があります（Qwen の実行基盤の記述の食い違い、MMLU の ε の値の食い違い、命題1の定数の不一致）。命題1は仮定に依存し、導出ではありません。DAG 自体を LLM が作るため、依存の読み違いが前提を崩します。

#### 再現性、コード、ライセンス

論文は CC BY 4.0 です。論文は `https://github.com/adaptorch/adaptorch` を示していますが、2026-11-14 に取得したところ 404 で、到達できませんでした。公開されたコードは確認できていません。

#### VGDD への適合の判断

採用する考え方は、依存グラフの指標（幅、深さ、結合の密さ）で、決定的な規則によって構成を選ぶことです。LLM を呼ばずに決まるので、Kernel が LLM で可否を決めないという VGDD の原則と両立します。選択の理由を監査ログに残すことも、そのまま使えます。

採用しない考え方は三つです。第一に、埋め込みの類似度の整合スコアを、正しさの判定に使うこと。著者自身が、論理的な整合は保証しないと明記しています。第二に、理論から導いたスケーリング則を設計の根拠にすること。仮定に依存します。第三に、閾値を再校正せずに流用すること。

理由：改善の大半は、タスクの分解と合成から来ており、トポロジ選択に固有の効果は限られます。VGDD の今の実装は静的な構成で、この論文の仕組みは取り入れていません。

### 2.4 Towards a Science of Scaling Agent Systems

#### 書誌と査読の状況

- Google Research のブログ（2026-01-28、Yubin Kim と Xin Liu）と、arXiv 2512.08296 です。論文の著者は Google Research、Google DeepMind、MIT の20名（Yubin Kim、Ken Gu、Xin Liu ほか）です。

#### 中心の枠組み

### 2.8 Agentic Context Engineering（ACE）

#### 書誌と査読の状況

- arXiv 2510.04618。著者13名（Qizheng Zhang、Changran Hu、James Zou、Kunle Olukotun ほか。冒頭の2名が同等の貢献）。Stanford 大、SambaNova Systems、UC Berkeley。
- v1 が 2025-10-06、v3 が 2026-03-29 の現行版です。ICLR 2026 に掲載（本文の冒頭に表示）。32ページ。論文のライセンスは CC BY 4.0 です。
- 水準：本文確認（テキスト抽出）です。

#### 中心の枠組み

文脈（システムプロンプトと記憶）を、重みの代わりに、更新できる「進化する手引き（playbook）」として扱います。三つの役割を置きます。

- Generator：推論の軌跡を作ります。
- Reflector：成功と失敗の軌跡から、具体的な知見を取り出します。
- Curator：知見を、小さな差分（delta）の項目にまとめます。

文脈は、ID と、有用か有害かのカウンタをもつ項目（bullet）の集まりです。Curator の差分は、LLM を使わない決定的なコードでマージします。全面の書き直しはしません。新しい項目は追加し、既存の項目はその場で更新します。意味の埋め込みで重複を除きます。

論文は二つの問題を定義します。一つは、短く一般的な指示に収束して領域の知識が失われる brevity bias です。もう一つは、LLM による全面の書き換えで文脈が急に縮む context collapse です。AppWorld では、あるステップで 18,282 トークン、精度 66.7 だった文脈が、次のステップで 122 トークン、57.1 に崩れ、適応なしのベースラインの 63.7 を下回りました。

#### 実験条件と主な数値

- 主なモデルは DeepSeek-V3.1（思考なしのモード）です。Generator、Reflector、Curator に同じモデルを使いました。追加で GPT-OSS-120B、GPT-5.1、Llama-3.3-70B-Instruct も使っています。
- ベンチマークは AppWorld、FiNER、Formula（金融）、DDXPlus（医療）、BIRD-SQL です。比較対象は ReAct、ICL、MIPROv2、GEPA、Dynamic Cheatsheet です。保持した分割で評価しています。
- 要約の主張：平均でエージェントのタスクが 10.6%、金融が 8.6% 改善し、適応の遅延は平均で 86.9% 減りました。
- AppWorld の平均では、ReAct が 42.4、GEPA が 46.4、ACE のオフラインが 59.4、ACE のオンラインが 59.5 です。AppWorld のリーダーボード（2025-09-20 時点）では、ACE が 59.4、IBM CUGA（GPT-4.1）が 60.3 で同等です。著者は、CUGA は参考であり直接の比較ではない、と注記しています。
- 差分の更新の有無（AppWorld、test-normal の平均）：なしが 56.9、ありが 70.3 です。
- 正解ラベルなしの場合、FiNER のオンラインでは、ACE がベースラインを下回りました（67.3、マイナス 3.4）。
- 頑健性：Reflector を意図的に有害にして挿入した実験では、毎回挿入すると 66.7（ベースラインより低い）、5回ごとで 76.1、50回ごとで 78.2 でした。

#### 限界

- 著者の述べる限界：十分に強い Reflector に依存すること、信頼できるフィードバック（正解ラベルや実行結果）がないと劣化しうること、豊かな文脈が要らないタスクでは効果が小さいこと、反復の回数が多すぎる（たとえば10回）と性能が下がること。
- こちらから見える限界：主な比較は単一のモデルで、各設定が1回の報告です。分散や信頼区間は、本文で確認できていません。採用の判断は Curator の規則とカウンタに依存し、独立した承認の主体がいません。効果の一部は、文脈が長くなったこと（入力トークンが約 117% 増えた）にも依ります。

#### 再現性、コード、ライセンス

コードが `https://github.com/ace-agent/ace` にあり、ライセンスは Apache-2.0 です（GitHub の API で確認、最後の更新は 2026-08-24）。プロンプトは付録に載っています。

#### VGDD への適合の判断

採用する考え方は次のとおりです。

- 生成、分析、編集の役割の分離。
- 全面の書き換えを禁じて、項目単位の差分だけを許す設計。ID と、由来のメタデータをもつ項目は、監査と取り消しがしやすくなります。
- マージを、LLM ではなく決定的なコードで行うこと。VGDD の、Kernel は LLM で可否を決めないという原則と合います。

採用しない考え方、または不足とする点は、ACE の Curator が提案と採用を同じ系の中で行うことです。VGDD では、Curator に相当するものの出力は「提案」にとどめ、採否は別の系統（検証器と人）が決めるべきです。また、有用か有害かのカウンタを、Generator の自己申告に頼る設計は、評価に合わせた見かけの改善（評価のゲーミング）に弱くなります。

安全上の注意：Reflector が毎回でなければ有害な提案に耐えるという結果は、1回の有害な提案が通ることを許す、とも読めます。VGDD では、そうした提案を採用の関門で止めることが要ります。

関連：VGDD の「前の試行の記録」（第4節、第5節の候補6）は、ACE の項目単位の更新を取り入れたものではありません。設計が近いのは、更新の対象を項目単位にし、全面の書き直しを避けるという点だけです。

- 内容：エージェントが運用の規則をスマートコントラクト（ブロックチェーン上で自動で実行されるプログラム）として「立法」し、決定的なソフトウェアが「執行」し、人間が所有者の連鎖を通じて「裁定」する、三権分立（Separation of Power）です。EVM 互換のレイヤー2 上の3階層のコントラクトで構成します。50 から 1000 体のエージェントによる、事前登録の実験を設計していますが、要旨には結果の記載がありません。
- VGDD との類似：立法、執行、司法の三分割、憲法的な階層、人間への責任の帰属、実行時の強制です。VGDD の概念に最も近い先行研究です。
- VGDD との違い：対象は組織をまたぐ「エージェント経済」で、開発のライフサイクルではありません。強制はブロックチェーンで行います。人間が司法（紛争の裁定）の側にあり、立法はエージェントの側にあります。VGDD は、人が立法の効力を持ち、AI は起草だけです。配置が逆です。コードの公開は確認できていません。
- 成熟度：論文のみです。

#### From Logic Monopoly to Social Contract（Ruan、NetX Enterprise Framework。arXiv 2603.25100）

- 2026-03-26、単著、143ページの working paper です。要旨確認です。
- 内容：各エージェントが、計画、実行、評価を独占する状態（Logic Monopoly）を問題とし、立法、執行、司法の分離を、契約を中心に実装します（TEE と呼ばれる隔離された実行環境、ブロックチェーン、8つのスマートコントラクト、ガバナンスのハブ）。NetX 社のホワイトペーパーに「Judiciary Layer」があります（`https://netx.gitbook.io/netx-docs/whitepaper/netx-enterprise-framework-nef/vi.-netx-enterprise-framework-the-judiciary-layer`。200 の応答は未確認のため、参考扱いです）。
- 類似：司法の層が、立法を上書きしたり、実行を止めたりする構造は、VGDD の独立した審査に近いです。
- 違い：企業間の経済とブロックチェーンが前提です。人間の役割は要旨で不明です。実証は、二次資料の数値（攻撃の成功率 84.3%、欺瞞 31.4%）が中心で、自身の枠組みの評価は不明瞭です。
- 成熟度：論文と、ベンダーの設計文書です。実装の公開は未確認です。
- 注意：AgentCity と Logic Monopoly は同じ著者で、どちらもコードを確認できておらず、査読もありません。

#### PEA：Policy-Execution-Authorization（arXiv 2604.23646）

#### Microsoft Agent Governance Toolkit（AGT）

### 3.4 ワークフローエンジン

- LangGraph：interrupt（割り込み）で停止し、チェックポインタに状態を保存し、無期限に待ってから Command で再開できます。永続的な実行（durable execution）は、チェックポインタを使うと有効になります。`https://docs.langchain.com/oss/python/langgraph/interrupts`、`https://docs.langchain.com/oss/python/langgraph/durable-execution`。MIT、約4.5万のスター。
- Temporal：Signal による承認の待機（待っている間は計算資源を使わない）、イベント履歴の再生による障害からの復旧。`https://docs.temporal.io/ai-cookbook/human-in-the-loop-python`。MIT、約2.4万のスター。
- VGDD との違い：どちらも承認の待機と復旧の基盤で、「誰が何を承認する権限を持つか」という統治の意味づけを持ちません。補完の関係にあります。人の承認を待つ仕組みの比較は、第三者の記事に依るため、優劣は断定しません。

### 3.5 統治された自己改善

### 4.3 VGDD の行についての補足

各観点で VGDD の状態を、根拠となる資料とともに補足します。

1. 統治権限の分離と独立性：`capabilities.json` の役割の表と、C1 から C3 の適合性テストで、役割ごとの権限を確かめています。ただし、行政の長が自分でソースを書かないことは約束（promise）のままです（`docs/kernel.md` の ADR-001）。司法は、judge と Codex の二系統ですが、同じ見落としをする可能性は残ります（SPEC 第12節）。
2. 人間による最終統制：仕様の承認、統合の承認、裁定、停止と再開は、オーナーだけが行えます（SPEC 第2節、第4節、第8節）。
3. 実行時に強制される権限制御：フック、OS の sandbox、worktree の隔離、別プロセスで強制します。強制の穴は `known_gaps` に公開されます。フックの Bash の判定は文字列の照合で、回避の余地があることを、仕様が認めています（SPEC 第12節）。
4. 動的なエージェント構成：役割ごとのモデルは静的に決まります（ADR-044。「一部（静的）」）。作業員の並行数は既定で1で、並行はキューで明示したときだけです。
5. グラフ型のタスク実行：票の依存（`depends_on`）と、統合のキューがあります。ただし、AdaptOrch のように、グラフの指標から構成を選ぶ仕組みはありません。
6. 経験記憶と意味検索：自動修正のときに、前の試行の記録（司法の指摘、変えたファイル、前の作業員の報告）を、次の作業員への指示に添えます（SPEC 第5節）。意味検索はありません。
7. 自己改善の安全性：自律的な改善はしません（ADR-021 は「後回し」）。法律の改正は、人が承認する手続きだけです。
8. 開発ライフサイクル全体への適用：仕様の承認、作業、司法、統合までを一続きに扱います。実稼働の記録は、題材のアプリ「つぶやき業務ログ」1件だけです。
9. 非開発業務への転用性：なし。現在は開発の工程に特化しています。
10. 非エンジニアの操作性：オーナーの操作窓口（SPEC 第8b節、`127.0.0.1` で動く画面）はあります。しかし、非エンジニアの人が操作して確かめた記録は、材料にありません。
11. 監査可能性と再現性：ハッシュチェーンとチェックポイントがあります。外部への固定（アンカー）はなく、同じ機械の管理者権限を持つ人は記録を書き換えられます（SPEC 第10節）。ほかの人の手元での再現は、一つの環境（macOS、Node 25）の clone で確かめた記録があるだけです（`docs/validation.md`）。
12. 性能、費用、保守性：単一の AI や、通常のマルチエージェントとの比較実験はありません。予算の台帳（SPEC 第9節）はありますが、トークンと金額の厳密な上限は保証しないと、仕様に書かれています。

### 5.2 VGDD の独自の設計

ここでの「独自」は、先行研究の中に同じ配置が確認できなかった、という意味です。優れていると主張するものではありません。根拠は、VGDD 自身の文書に書かれた設計です。

1. 人が立法の効力と最終の承認を持ち、AI は起草だけという配置。SPEC 第4節は、仕様を起草するのは誰でもよいが、効力はオーナーが仕様の指紋（SHA-256）を承認した記録だけが与える、と定めています。承認の記録は、行政が書けない場所に置かれます。AgentCity は、立法をエージェントの側に置くので、配置が逆です。
2. 承認が、対象と範囲に結びつくこと。仕様が1文字でも変われば承認は効かなくなります。承認は法律の系統（`policy_line`）にも結びつき、権限の表が読めなければ、どの承認も効きません（SPEC 第4節の 5 と 6、不変条件 INV-06）。
3. 「司法が使えない」ことを、判定として扱わないこと。判定のファイルがない、壊れている、CLI の応答が空、という場合は、合格にも差し戻しにも数えません。申請を残し、同じ申請で3回続けば、オーナーの判断に回します（SPEC 第6節の 5）。
4. 司法の入力を、機械的に集めた差分、承認された受け入れ条件、決定的な監査の結果だけに限り、行政の説明を入れないこと（SPEC 第6節の 1）。
5. 統合できる主体を、裁判所とオーナーの朝の承認に限ること（SPEC 第7節）。

これらは、設計の記述と、適合性テストの結果で確かめられています。ただし、他の構成や、他の人の手元で同じことが成り立つかは、確かめていません。

### 5.3 新しい技術的貢献の候補

以下は、検証すべき仮説です。各項に、近い先行研究と、まだ示せていないことを書きます。

#### 候補1：人が主権者で、AI は起草だけという三権分立を、開発の工程で実稼働させた記録と、適合性テスト

仮説：人が立法の効力と最終の承認を持ち、AI を起草と作業に限る三権分立の配置を、開発の工程で実際に動かし、その規則を適合性テストで検査できる。

- 近い先行研究：AgentCity（三権分立。ただし立法はエージェント、人間は裁定）、Logic Monopoly と NetX（司法の層）、MS AGT（実行時の強制と人間の承認。ただし役割の分離はない）、Spec Kit と OpenSpec（仕様の合意。ただし強制はない）。
- VGDD が持っているもの：適合性テストが 527 件（法律 p0.4.14。2026-11-14 にこのリポジトリの写しで実行し、525 件が合格。合格しなかった 2 件は、配置済みの設定ファイルがこの写しにないことによる）、実稼働の記録は、題材アプリ「つぶやき業務ログ」の票と、`docs/validation.md` に記された事例（仕様の承認前の申請を blocked にした例、裁定が4件あった例など）。
- まだ示せていないこと：
  - 実稼働の記録は、一つの題材、一人のオーナー、一つの環境（macOS、Claude Code）です。他の構成での再現は、新しい clone での公開の手順による試験が、macOS と Node 25 の一つの環境だけで確かめられています。Windows と Linux、ほかの人の手元は、確かめていません。
  - 単一の AI や、通常のマルチエージェントと比べて、品質、費用、速度がどうなるかの比較実験は、ありません。
  - 司法の独立性（同じ系列のモデルによる相関した見落とし）が、実際にどの程度問題になるかを測っていません。
  - 非エンジニアが、承認の役を実際に担えるかを示していません。

#### 候補2：強制していない約束を、権限の表に promise として公開する規律と、権限の表から適合性テストを生成する仕組み

仮説：強制の層を持たない約束を、権限の表に `promise` と明記して公開させ、権限の表の各権限に `probes`（試験する操作）と `expect`（期待する判定）を持たせると、表から適合性テストを機械的に生成でき、表と実装の食い違いが試験の失敗として現れる。

- 近い先行研究：AgentSpec（事象、述語、強制の動作の記述言語）、OPA と Cedar（宣言的なポリシー）、MS AGT（YAML のポリシーと適合テスト 992 件）。これらは、ポリシーの記述と、実装の試験を持ちます。
- VGDD が持っているもの：`capabilities.json` の各権限に、`allowed`、`enforced_by`、`probes`、`expect`、`known_gaps` があります（SPEC 第2節）。適合性テストの M 群は、どの権限にも確かめ方があり、参照した試験が合格していることを自己検査します（SPEC 第11節）。`docs/kernel.md` の第7節に、「適合性テストが規範の表から試験を生成するので、表と実装の食い違いは試験の不合格として現れる」と書かれています。
- 先行研究との違いの見込み：「強制していないことを、表の中で、約束として公開する」という規律を、仕様の義務（MUST）にしている点です。AGT などが、強制していない約束を公開しているかどうかは、調査していません。
- まだ示せていないこと：
  - 約束の公開が、利用者の誤解を実際に減らすかどうか。
  - 表から試験を生成する方式が、手で書いた試験より、見落としを減らすかどうか。比べていません。
  - 表の `probes` の網羅の程度を、独立に評価していません。実際、`docs/kernel.md` の不変条件の表では、INV-03、07、08、11 は「一部」、INV-09 は「対象外」です。

#### 候補3：統治の仕組み自身の穴を「判例」にして、前の版にかけて新しい判例だけが落ちることを確かめてから改正する手続き

仮説：統治の仕組み自身の穴が見つかったら、その穴を再現する判例（適合性テスト）を書き、前の版にかけて、新しい判例だけが落ちることを確かめてから、別系統の監査と、オーナーの承認を経て改正すれば、試験が空回りしていないことを示しながら、仕組みを改正できる。

- 近い先行研究：論文1の層状ゲート（検証器が候補を通した場合だけ採用。検証器の変更は追加だけの単調な変更に限る）、論文5の「既知の安全な版の管理と、試験したうえでの巻き戻し」。DGM は、ベンチマークによる採否です。ソフトウェア工学の一般的な回帰試験や、変異試験の考え方も近いと考えられますが、材料では調べていません。
- VGDD が持っているもの：`docs/validation.md` の例3と、`docs/kernel.md` の第3節。たとえば、p0.4.2 の実装では、G15（Codex の判定ファイルがない）と G19（judge の CLI の空の応答）の場面で、片方の司法の APPROVED だけで統合されていました。この穴を判例にし、p0.4.3 で直しました。p0.4.2 にかけると新しい判例が落ちる（p0.4.3 の時点で 66 件）ことを確かめています。p0.4.4 では 13 件、p0.4.7 では p0.4.6 にかけて 8 件が落ちています。
- まだ示せていないこと：
  - これらの穴の発見は、行政の長の点検と Codex の監査によるものです。この手続きが、穴の見落としを減らすかを測っていません。
  - 手続きの各段階（別系統の監査、憲法審査、オーナーの承認）が、それぞれどれだけ効いたかの分離ができていません。
  - 改正の履歴は、一人のオーナーの一つのプロジェクトに限られます。
  - 憲法審査の結果は、公開されていないので、第三者は確かめられません（`docs/validation.md`）。

#### 候補4：権限の差分（Authority Delta）

仮説：権限の表の変更を、機械的に、「締める」「緩める」「分類できない」に分類し、緩める変更を、AI の改善の提案が通る通常の経路に乗せない。

- 状態：試作です。`vgdd/next/` にある起草段階のもので、実装済みとは書けません。
- 近い先行研究：論文1の 9.1 節（権限の境界や検証器を広げる経路への懸念。critic の更新は単調な変更に限る）、論文5の表12（目標と安全の制約の変更には人間のレビューを必須にする）、Progent（最小権限の記述言語）、OPA と Cedar（ポリシーの分析）。ポリシーの変更の差分を分類する研究は、今回の検索では確認していませんが、調べた範囲が限られています。
- まだ示せていないこと：
  - 分類が、実際の権限の表の変更に対して、正しいか（取りこぼしや誤分類）を示せていません。
  - 「分類できない」と判定されたものの割合と、その扱いの手間を示せていません。
  - 実運用で、緩める変更が、実際に別の経路に乗って人の承認を受けた記録が、まだありません。

#### 候補5：編成案の検証

仮説：動的なエージェントの編成を、承認済みの役割の型を上限とする範囲の中の、データとして検査すれば、動的な構成を許しながら、権限が広がらないことを機械的に確かめられる。

- 状態：試作です。`vgdd/next/` にある起草段階のもので、実装済みとは書けません。今の VGDD の実装は、静的な構成です（第4節）。
- 近い先行研究：AdaptOrch（依存グラフの指標で、決定的な規則によってトポロジを選ぶ）、論文4（構成の選択をタスクの性質に基づいて条件つきにする。ただし回帰式をそのままゲートにはしない）、MS AGT（委任、メッシュ）、DGM と ADAS（構成の自己進化。ただし採否はベンチマーク）。不変条件 INV-03（委任によって権限が増加しない）は、今の実装では「一部」で、委任の連鎖での権限の継承は試していません（`docs/kernel.md`）。
- まだ示せていないこと：
  - 検査が、実際に権限の拡大を防ぐことの、適合性テストによる確認。
  - 動的な編成が、静的な構成より、品質や費用の面で良いかどうかの比較。論文4の結果（多くのタスクで複数エージェントが単一より悪化）を踏まえると、利得があるかどうか自体が、検証すべき問いです。
  - 編成の検査が通るもののうち、人が見て不適切なものの割合。

#### 候補6：司法の結果からだけカウンタを更新し、司法には渡さない経験の記録

仮説：経験の記録（項目と、有用か有害かのカウンタ）の更新を、司法という独立した審査の結果だけに結びつけ、その記録を司法の入力には渡さなければ、ACE が抱える、自己申告に頼る評価のゲーミングと、司法の独立性の汚染の、両方を避けられる。

- 状態：試作です。`vgdd/next/` にある起草段階のもので、実装済みとは書けません。今の実装にあるのは、前の試行の記録を作業員への指示に添える最小の形で、司法には渡しません（SPEC 第5節、第6節の入力は変えない）。
- 近い先行研究：ACE（有用か有害かのカウンタ。ただし Generator の自己申告に頼り、採用は同じ系の中）、論文2（保存、反省、経験の段階。経験への格上げに人の承認を求める設計の案）、論文1（提案と採用を分ける）。
- まだ示せていないこと：
  - カウンタが、実際に作業員の成功率や、差し戻しの回数を改善するか。ACE のような比較実験は、していません。
  - 司法の結果が、カウンタの信号として十分に信頼できるか（二つの司法が同じ見落としをする場合を含む）。
  - 記憶が汚染されたときの影響を、ACE の頑健性の実験のような形で測っていません。

### 5.4 まとめ

VGDD の独自の設計として根拠を挙げられるのは、人が立法の効力を持つ配置、承認が対象と範囲に結びつく仕組み、司法が使えないことを判定として扱わない規則などです。これらは、VGDD 自身の文書と、適合性テストの結果で確かめられています。

新しい技術的貢献の候補として挙げたものは、どれも、仮説の段階にあります。特に候補4から6は試作で、効果を示すデータはまだありません。候補1から3も、一つのオーナー、一つの題材、一つの環境での記録に基づいています。第三者による再現と、比較実験が、示すべき次の課題です。
