## 1. 何であり、何でないか

ここにあるのは、次の問いに答えるための部品と試験である。

> AI が編成や規則の改善を提案できるようにしても、三権分立と Kernel の強制を保てるか。

部品はどれも、LLM を使わずに入力を検査する関数である。検査に通っても効力は生じない。効力を与えるのは、稼働中の Kernel の窓口と人の承認であり、そこへのつなぎは未着手である。

**この試作で確かめたのは、検査の論理が、用意した攻撃の例に対して働くことまでである。** 次のことは確かめていない。

- 稼働中の Kernel につないだときに、役割の分離が実際に強制されること
- 経験や改善提案が、AI の仕事の成功率や品質を上げること
- 用意していない攻撃を止められること

採用するには、法律の改正の手続き（起草、憲法審査、オーナーの承認）が要る。

依存パッケージはない。Node.js 22 以上で動く（確かめたのは Node 25.6.0・macOS）。

```sh

node vgdd/next/bin/authority-delta.mjs 旧版.json 新版.json
```

### 3.0 共通の語彙（`lib/vocab.mjs`）と橋渡し（`lib/bridge.mjs`）

部品は別々に作ったので、最初は継ぎ目に食い違いがあった。裁判所のスクリプトの役割名が部品ごとに 3 通りあり、票の ID、申請の指紋、系統の書式も違った。結合の試験（8 つの部品を 1 つの流れで通す）では、試験の側で値を変換した箇所が 19 件あった。食い違いの一部は穴になっていた。

- セキュリティ審査の役割が、経験の記録では司法とみなされず、経験が渡った。
- 改善提案で、提案者が `claude`、審査者が `anthropic` と名乗ると、別の系統として通った。
- 役割が作業員でも、種類がスクリプトなら、経験の評価を更新できた。

そこで、語彙を 1 つの部品に集め、全部の部品がそこから読む形にした。今は、変換なしで流れが通る。

| 語彙 | 決めたこと |
|---|---|
| 役割 | 権限の表（`capabilities.json`）の名前を正とする。表にない名前は使えない。司法かどうかは、表との完全一致で決める。権限の表にまだない役割が 3 つある（`codex_security`、`reaper`、`trace_importer`）。配線の改正で表に足す候補として、分けて持つ |
| 行為者 | 全部の部品が同じ形 `{ role, kind, id, lineage }` を受けて記録する。役割と種類（人、AI、スクリプト）が合わなければ拒む |
| 系統 | 知っている系統（`claude`、`codex`、`human`、`script`）だけを受ける。別名で別の系統を装えない。司法と立法補佐の役割は、系統が表で決まっていて、別の系統を名乗れない。系統を足すのは、語彙の変更になる |
| 票の ID | 宣言の形 `{ prefix, digits }`（既定は `T-` と 3〜4 桁）。大文字と小文字を区別する。領域パックが宣言を持ち、実行の状態、追跡、経験が同じ宣言を使う |
| 指紋と参照 | 指紋は `sha256:` と 64 桁。申請と統合の参照は、40 桁の 16 進か `sha256:` の形 |
| 時刻 | 時差つきの ISO 8601（秒まで必須。時差は `Z` か `±HH:MM`） |
| 拒否の形 | 状態を書く関数の拒否は、全部の部品で `Refused('guard_violation')` と、違反の一覧 |

設定の持ち方もそろえた。実行の状態は、記録の中のオーナーの出来事が設定を決める。経験、追跡、改善提案は、開く側の引数で受け、書く行に設定の写しを残す。写しと食い違う設定で開くと、オーナーの移行の記録があるまで、書き込みを止める。

過去の記録との互換は取っていない（まだどこにも配置していないため）。規則の版は、実行の状態が `rs.v4`、追跡が `tr.v4`、経験が `ex.v2`、改善提案が `im.v5`、外部への固定が `an.v2` である。古い版の行は、どの部品でも、オーナーの移行の記録（epoch）に覆われるまで書き込みを止める。

### 3.0b 記録の部品の、落ちた後の復旧（`lib/chain.mjs`）

追記は、「行を書いて確定する。次に、末尾の印（最後の番号とハッシュ）を、一時のファイルに書いて確定し、置き換える」の順で行う。最初の版は、この途中でプロセスが落ちると、記録が壊れた扱いになって書き込みが永久に止まり、直す道具も手順もなかった。

今は、落ちた跡として説明のつく 2 つの形だけを、次の追記の時に自動で復旧する。

| 形 | 何が起きたか | 何をするか |
|---|---|---|
| 行は書けたが、末尾の印が古い | 印の後ろに、鎖として正しい完全な行が、ちょうど 1 つある | 印を進める |
| 行が途中まで | 末尾が改行で終わっていない。最後の改行までは、印と合う | 書きかけの部分を別のファイルに退避して、切り捨てる |

**それ以外の形は、今までどおり止める。** 印の後ろに 2 行以上ある、途中の行のハッシュが合わない、行が印より少ない、印がない・壊れている、などである。

- **末尾の印は、自動では作り直さない。** 作り直せると、「印を消して、末尾を切り詰める」書き換えが通るためである。印がない・壊れている記録は、人が、期待する末尾の番号とハッシュを渡したときだけ直せる（`repairHead`）。この関数は行為者を確かめないので、AI が呼べる場所に置かない。
- 復旧したことは、必ず別のファイル（`<記録>.recovery.jsonl`）に残す。
- 落ちたプロセスが残したロックは、同じ機械で、持ち主のプロセスがもう生きていないと確かめられたときだけ引き継ぐ。
- 復旧は、確定した行（印が指す範囲）には触れない。1 つ目の形は、印を、すでにある行に追いつかせるだけである。攻撃者が、鎖として正しい偽の行を足した場合は、印も一緒に書き換えた場合と同じ結果で、新しい力を与えない。規則に合わない行は、各部品が再生のときに拒む。

前提は、手元のディスクである。ネットワークのファイルシステムでは、ロックと置き換えの原子性が保証されない。

独立した審査（4 回目）の後に、次のことを足した。

- **書く側も記号リンクをたどらない。** 本体、末尾の印の一時ファイル、復旧の記録、退避のファイルは、開く前に通常のファイルであることを確かめ、記号リンクをたどらない開き方（`O_NOFOLLOW`）で開く。開いた後にも、開く前と同じファイルで、リンクの数が 1 であることを確かめる。記号リンク、ハードリンク、通常のファイルでないもの、記録のフォルダ自身が記号リンクのときは `unsafe_file` で止める。前に落ちて残った末尾の印の一時ファイルは、通常のファイルのときだけ消して作り直す。
- **ハッシュと書く行を、同じ値から作る。** 追記の本体を JSON として写し、写した値が元と同じ正規形にならないもの（`toJSON` を持つ値、疎な配列など）は `not_canonical` で拒む。前は、追記が成功した後に記録が読めなくなった。
- **書いたとおりの綴りの行だけを受ける。** 行を解析して書き直した文字列が元の行と違うもの（重複したキー、空白、エスケープの違い）は、鎖が通らない（`not_canonical_line`）。別の言語の解析器が違う意味で読む行を、鎖として通さないためである。代わりに、ほかの道具で整形し直した記録は読めなくなる。
- 読み手も、末尾の印がないのに行がある記録を止める（前は、1 行だけなら正常・0 件と返した）。書き手が自動では直せずに止まり続ける形（印の後ろに、鎖につながらない完全な 1 行）は、`verify()` が `pending: 'unrecoverable'` で知らせる。
- 遷移の検査（`check`）に渡した配列を検査が変えても、次の行の番号と前のハッシュは変わらない（検査の前に決める）。
- ロックの持ち主の情報を書けなかったときは、ロックを消さずに止める（自分のものと確かめられないロックに触らない）。

### 3.1 権限の差分（`authority-delta.mjs`）

権限の表（`vgdd/kernel/capabilities.json`）の変更 1 つずつを、次の 4 つに分ける。

| 分類 | 例 |
|---|---|
| 締める | 許可する役割を減らす。強制の層を足す。確かめ方（probe・判例）を足す。不変条件を強める |
| 影響しない | 説明文の変更。穴の記載の追加。同じ系統の中で版が上がる |
| 緩める | AI の役割に許可を足す。フックの判定を拒否から許可に変える。強制の層を減らす。確かめ方を消す・書き換える。不変条件を弱める・消す |
| 分類できない | 規則にない欄の変更。穴の記載の削除。役割の識別の根拠の変更。法律の系統の変更。読めない入力 |

全体の分類は、最も重いものになる。分類できない変更は、緩める変更と同じ扱いにする。

**設計の判断。**

- 緩める変更と分類できない変更は、改善提案の通常の経路に乗せない。憲法審査が必須の経路に回す。どちらの経路でも、オーナーの承認は必須である。自動で採用するという値は存在しない。
- 確かめ方の書き換えは「削除と追加」として扱い、緩める側に数える。評価される側が、試験の中身を無害なものに差し替える経路を塞ぐためである。
- 適合性テストが実際には実行しない probe の追加は、締める側に数えない。
- 法律の系統（`kernel_version` の `pN.N`）の変更は分類できないとする。承認の有効性が系統に結び付いているので、系統を戻すと、無効になった承認が復活するためである。

### 3.2 改善提案の記録（`improvement.mjs`）

提案の対象は 6 つの階層に分ける。経験、手順、編成、法律、検証器、憲法である。

```
提案 ─→ 評価 ─→ 審査 ─→ 採用 ─→（取り消し）
  │       │       │       └ 人のオーナーだけ。提案の指紋と法律の系統に結び付く
  │       │       └ 司法の役割。提案者と別の主体、別の系統のモデル
  │       └ スクリプトか人。試験の合格数の前後を証拠として出す
  └ 誰でも（AI も）。未決の数に上限
```

主な規則を挙げる。全部で 26 のガードがある。

- 採用できるのは、人のオーナーだけである。却下と取り消しもオーナーだけが行う。
- 提案者、評価者、審査者、採用者は別の主体でなければならない。評価を出せるのは、裁判所のスクリプトと人のオーナーだけである。審査できるのは、権限の表にある司法の役割だけである。
- 採用には、承認（APPROVED）を出した司法の系統が 2 つ以上要る（今の語彙では claude と codex の両方）。司法の系統は役割で決まり、申告で変えられない。提案者の系統の申告は使わない。同じ系統の司法が何体承認しても、系統は 1 つと数える。差し戻しは、系統を問わず効く。
- 片方の系統の司法が使えないときの出口は、人のオーナーが採用の入力に理由を付けて解くこと（`cross_lineage_waiver: { reason }`）である。理由は採用の行と状態に残る。承認が 1 つもない採用は、解いても通らない。
- 評価、審査、採用は、提案の今の指紋に結び付く。評価の後に中身を変えると、評価と審査は効かなくなる。
- 提案者の説明（rationale）は、指紋にも審査の入力にも入れない。審査の入力は機械が組み立て、その指紋を審査の記録に結び付ける（SPEC §6-1 の司法の独立と同じ考え方）。
- 試験の合格が減る提案、試験の数が減る提案は採用できない。試験を足す提案は、足した試験が前の版で落ちることの証拠が要る（空回りの試験を足せない）。
- 法律を緩める提案、検証器を消す・緩める提案、憲法への提案は、憲法審査の承認がなければ採用できない。Claude の系統の提案者の場合は、「憲法審査（Claude）の承認、Codex の司法の承認、オーナーの採用」の 3 つがそろって通る。
- 法律の提案の中身は、分類に使った権限の表と同じものでなければならない。表以外のファイルを含む提案は、常に憲法審査の経路に回す。
- 差し戻しは提案に残る。差し戻した審査者が今の版を承認するまで採用できない。取り下げて出し直しても引き継ぐ。別の審査者を選び直して通すことはできない。引き継ぐのは、同じ中身の提案と、同じ系統か同じ id の提案者が同じ対象に出した提案である（系統の申告を変えるだけでは外れない）。
- 行き止まりは、オーナーが理由を記録して差し戻しを解くことで解ける。AI と司法は解けない。
- 記録の各行は規則の版を持つ。規則を変えたときは、オーナーが移行の記録を書いて、古い行を覆う。

### 3.3 経験の記録（`experience.mjs`）

項目は 2 層ある。1 つの出来事から得た「反省」と、別々の票の 2 件以上から帰納した「経験」である。生の記録は写さず、証拠への参照だけを持つ。

- 出どころのない項目は作れない。信頼の度合い（根拠あり、未検証の仮説）は、出どころの種類から機械が決める。呼び出し側は選べない。
- 追加は誰でもできるが、候補としてだけ入る。採用済みに上げられるのは、人のオーナーだけである。
- 更新は項目の単位の追加だけである。全体を書き換える操作は存在しない。
- 役に立ったかのカウンタは、裁判所の側のスクリプトが、司法の結果を証拠にしてだけ更新する。同じ証拠は 1 回しか数えない。
- 取り出しは、行為者を必須で受けて記録する。取り出せるのは行政の側の役割だけである。評価に数えるのは、票の着手から申請までの間に、その票に着手した行為者（か、割り当てられた作業員）が取り出した分だけである。判定が出た後の取り出しは数えない。
- AI は項目を引退させられない。都合の悪い経験を消せない。スクリプトによる自動の引退は、候補の項目にだけ効く。オーナーが採用した項目は、有害の評価が閾値を超えても自動では引退せず、オーナーへの注意として出る。
- 司法の役割には渡さない。経験が審査の入力に混ざると、行政が経験を通じて司法に働きかける経路になるためである。
- 取り出した項目は、引用の囲みに入れ、囲みの中の命令に従わないよう指示を付けて渡す。候補と未検証の仮説は、その旨を明記する。本文は伏せ字を通す。
- 命令らしい文を含む項目は、拒否せずに印を付ける。印のある項目は、オーナーが確認を明示しなければ採用済みに上げられない。

**検索は字句の一致である。意味検索（埋め込み）ではない。** 戻り値に `searchKind: 'lexical'` を入れている。点数の関数を差し替える口はあるが、埋め込みは実装していない。

**ACE（arXiv 2510.04618）との違い。** 項目の単位の差分で更新する点と、統合を決定論的なコードで行う点は ACE に倣った。違うのは、採否とカウンタを系の外に出した点である。ACE は、生成・分析・編集の 3 役を同じモデルが担い、カウンタは系の内側で更新する。ここでは、昇格は人、カウンタは司法の結果、取り出す先から司法を除く、とした。この違いが仕事の成績にどう効くかは測っていない。

### 3.4 仕事のグラフ（`taskgraph.mjs`）

票の集まりを、依存を辺とするグラフとして読む。

- 循環、存在しない依存、id の重複、形の違う節を拒む。壊れたグラフは実行に渡さない。
- 着手してよい節と、着手できない節の理由（未承認、依存の待ち、依存が止まっている）を返す。未承認の節や止まった節は、それに依存しない節を妨げない（INV-12）。
- 同時に動かしてよい組を選ぶ。触る範囲が重なる節は同じ組に入れない。同時の数は、人が決めた上限を超えない。
- 構成の勧め（単一、並列、段ごと）を理由つきで返す。**既定は単一**である。並列を勧めるのは、今すぐ着手できる節が 2 つ以上あり、範囲が重ならず、上限が 2 以上で、高リスクの節を含まないときだけである。

AdaptOrch の指標（並列の幅、依存の深さ、結合の密度）は計算して返すが、勧めの決定には使っていない。AdaptOrch の閾値は VGDD の仕事で校正していないためである。

### 3.5 編成案の検査（`team.mjs`）

編成案は「承認済みのどの役割の型を、何体、どの範囲で、誰の委任で動かすか」を書いたデータである。

- 使えるのは、承認済みの役割の型だけである。その場で新しい役割は作れない。
- 範囲は、票の承認された範囲の部分集合でなければならない。包含を判定できない書き方は違反にする。
- 委任された子の範囲は、親の範囲の部分集合である。委任の深さに上限がある（INV-03 の一般化）。
- 司法の型は委任されず、委任もしない。同じ主体が行政と司法の両方に現れない。
- 司法が最低 1 体いる。行政のどの構成員とも系統の違う司法が 1 体以上いる。
- 人の席、立法、オーナーの権限で動く処理（裁判所、夜間の代行）は、編成に入れられない。
- 行政の数と構成員の総数は、上限を超えない。編成案が上限の引き上げを求めることはできない。
- 検査に通っても、`requires_approval: true`、`effect: 'none'` を返す。効力は与えない。

### 3.6 領域パック（`domain.mjs`）

業務ごとの部分（仕事の単位、成果物の形、工程と関門、決定論的な監査、司法の観点、保護する範囲）を宣言する形と、その検査である。検査は、領域パックが統治の核を弱めていないことを見る。

- 司法を無効にできない。司法の入力に使える名前は許可リストで固定し、行政の説明を入れられない。
- 関門をすべて消すことはできない。人の承認の段が最低 1 つ要る。
- 役割、権限、予算、停止を定義する欄は、どの階層にも持てない。未知の欄も違反にする。
- 統治の核のパスを保護から外せない。
- 監査のコマンドは引数の配列で、実行ファイルは許可リスト（今は `npm` と `node`）に限る。sandbox の中で動かす宣言が必須である。
- 決定論的な監査が 1 つもないパックは、その旨を決まった文で公開しなければならない。

例は 2 つある。`software-dev.json` は、今の実装が前提にしていることの書き写しである。`research-report.json` は開発以外の例で、**実際に仕事を回したことはなく、監査のコマンドは実在しない。**

### 3.7 実行の状態の記録（`runstate.mjs`）

今の Kernel では、仕事の状態の移り変わりが、裁判所と夜間の代行のスクリプトと、票のファイルの書き換えに埋め込まれている。これを、追記専用の記録の上の状態機械として取り出した。記録から状態を作り直せるので、途中で落ちても続きから再開できる。

出来事と、起こせる者は次のとおりである。

| 出来事 | 起こせる者 | 状態の移り変わり |
|---|---|---|
| 設定（config） | 人のオーナー | 記録の最初の出来事として必須。上限、同時の数、法律の系統、必須の審査の一覧、夜間の保留を記録に固定する |
| 計画（plan） | 行政、オーナー | 節を足す。足した節は未承認で始まる。既存の節は書き換えられない（置き換えは新しい節として行い、承認は引き継がない） |
| 承認（approve） | 人のオーナー | 節の仕様の指紋と法律の系統に結び付く |
| 着手（start）、申請（submit） | 行政、行政の代行 | ready → in_progress → review |
| 判定の取り込み（verdict） | 裁判所のスクリプト | review → merged、held、in_progress（差し戻し）、blocked のどれか |
| 統合の承認（release）、裁定（rule）、再開（unblock）、差し戻しの取り消し（annul） | 人のオーナー | held → merged など |
| 期限切れの回収（expire） | スクリプト | in_progress → ready |
| 停止、再開、時計の訂正、規則の移行 | 人のオーナー | 停止中は、停止・再開・時計の訂正のほかをすべて拒む |

判定の取り込みでは、合否そのものは受け取らない。受け取るのは、監査の結果と、司法ごとの判定の一覧である。結果は部品の中で、SPEC §5〜§7 の規則を機械的に当てて決める。

- 申請の指紋が今の申請と違えば拒む（前の申請の合格を使い回せない）。
- 監査が不合格か未実行なら、司法が合格でも差し戻す。
- 必須の審査の全部に結果がなければ、「司法が使えない」とする。使えない審査が 1 つでもあれば同じ。状態は変えず、差し戻しにも数えない。同じ申請で通算 3 回になれば止める。
- セキュリティ審査の不合格は差し戻しで、裁定では通せない。
- 重大な指摘で判定が分かれたら止めて、オーナーの裁定を待つ。重大でない指摘だけで分かれたら、その旨を記録して合格にする（今の法律と同じ）。
- 差し戻しと着手の回数には上限がある。上限を超えたら止める。再開しても回数は戻らず、オーナーが追加の回数を与える。

**設計の判断。**

- 設定を、記録を開く側の引数でなく、記録の中のオーナーの出来事にした。最初の版は引数で受けていて、開き方ひとつで上限と保留を外せた（独立した審査の発見）。
- 実行中に緩める変更（上限を上げる、保留を外す、必須の審査を減らす、法律の系統を変える）は、作業中の節がないときだけ受ける。締める変更はいつでも受ける。
- 範囲の重なりは、統合されていない作業の全部（着手中、申請中、保留中、申請を持ったまま止まっている節）と比べる。
- 保護された範囲（領域パックの `protected` を設定に写したもの）と重なる節は、計画に入れられない。保護を後から足した場合も、重なる節は着手できない。
- 作業中の節も同じである。申請、判定の取り込み（合格でも差し戻しでも）、統合の承認（release）の時点で、節の範囲を今の保護と比べ、重なれば止める（blocked、理由は protected）。保護を足す設定（config）は、重なる作業中の節の一覧を返す。止めた節から統合に進めるのは、審査に合格した（または判定が分かれた）申請に対するオーナーの裁定だけである。ほかの出口は、オーナーの置き換えか、保護を見直した後の再開である。
- 時刻が戻っても追記は拒まない。期限の判定には、それまでの行の時刻の最大値を使う。実時間より 5 分以上先の時刻の行は書かせない。それでも時刻が進んでしまった記録は、オーナーが理由を付けて訂正できる。停止は、どの時刻の状態でも通る。
- 人以外が使える出来事の数と節の数に上限を置き、残りはオーナーのための枠にした。行政が枠を使い切っても、オーナーの停止と計画は通る。

**今の Kernel と合わせなかった点。** 着手に期限（lease）を付ける考え方は、今のスクリプトにない。差し戻しの理由のうち、領域に固有の前検査（範囲の外、HEAD の不一致、main との衝突）は出来事にせず、監査の不合格として入る前提にした。

### 3.8 追跡の記録（`trace.mjs`）

成果物の種類は 16 ある（目標、要件、設計、票、仕様の指紋、承認、申請、監査、判定、裁定、統合、受け入れ、リリース、障害、改善提案、経験）。つながりの種類と、つなげる成果物の組は、1 つの表で決めている。表にない組は拒む。

```
目標 ← 要件 ← 票 ← 仕様の指紋 ← 承認
                      ↑
                     申請 ← 監査、判定、裁定
                      ↑
                     統合 ← 受け入れ、リリース ← 障害 ← 対応の票
```

- 書けるのは、裁判所の側のスクリプトと、人のオーナーだけである。AI は書けない。行政が、自分の成果物に都合のよいつながりを作れない。
- つながりは不変である。取り消しはオーナーだけが行い、行は消さずに取り消しの記録を足す。
- 置き換え、派生、依存の循環は拒む。

問い合わせは 3 つある。

- **たどる。** ある成果物から、上流（要求の側）と下流（運用の側）へたどる。
- **充足の表。** 要件ごとに、票、今の仕様、承認、申請、監査、判定、統合、受け入れ、障害があるかをまとめる。
- **欠けの一覧。** 票のない要件、承認のない仕様、差し戻されたままの申請、受け入れのない統合、対応する票のない障害などを挙げる。

**充足の数え方（独立した審査で直した点）。**

- 承認は、今の仕様（置き換えられていない仕様）へのものだけを数える。今の仕様が 1 つに決まらない票は「未確定」とし、満たされているとは数えない。
- 判定は、種類ごとの最新の結論を見て、必須の種類が全部そろって合格のときだけ承認とする。必須の種類が分からない申請は、存在する種類だけで決め、その旨を出力に書く。
- 裁定で通せるのは、司法どうしの不一致だけである。セキュリティ審査の不合格は、裁定があっても差し戻しのままとする。
- 監査は、最新が合格のときだけ数える。
- 各段は「少なくとも 1 本ある」ことを言うだけで、全部が満たされたことではない。
- **欠けは「記録にない」ことを言うだけで、「行われなかった」ことの証明ではない。**
- 記録に規則に合わない行があれば、問い合わせの結果にその印を必ず付ける。

**今の Kernel の記録からの取り込み。** `linksFromEvidence` は、承認、夜間の合格、裁判所の出来事、判定、裁定、受け入れ、票の front matter から、つながりを作る純関数である。Kernel を変えずに使える。ファイルは開かない（呼び出し側が読んで渡す）。各記録の欄の名前は、書く側のスクリプトを読んで確かめ、箇所をコメントに残した。

### 3.9 外部への固定（`anchor.mjs`）

今の記録は、同じ機械の管理者が、記録と末尾のハッシュを一緒に書き換えれば検出できない。鎖があるのは操作の証拠と予算の台帳だけで、承認、裁定、夜間の合格、判定の記録には鎖がない。チェックポイントの記録そのものにも鎖がない。

この部品は、記録の集まりの「その時点の状態」を、1 つの値（32 バイトの SHA-256）にまとめる。この値を固定の値と呼ぶ。

- **状態の一覧（manifest）** を作る。記録ごとに、先頭からのバイト数、行数、そこまでの内容の指紋、鎖の検証の結果を持つ。前の一覧の指紋も持つので、固定の値どうしも鎖になる。一覧は手元にだけ置く。
- **固定の値**は、一覧の指紋である。外に出してよいのは、この値と記録の時刻だけである。記録の名前、パス、件数、中身は、固定の値からは分からない。
- **照合**では、手元の記録が、固定した時点までの内容を今も含んでいるかを確かめる。書き換え、切り詰め、行の抜き取り、記録ごとの削除を見分ける。
- 鎖のある記録は 3 つの方式（操作の証拠、予算の台帳、試作の記録）に対応した。鎖のない記録と、判定のファイルの集まりも対象にできる。
- 書けるのは、裁判所の側のスクリプトと人のオーナーだけである。対象の記録を減らす変更は、オーナーだけが、理由と名前を挙げて行える。裁判所のスクリプトは、都合の悪い記録を対象から外せない。
- 記録が「伸びただけ」でない食い違いは、黙って上書きせず、一覧と戻り値に残す。前の固定で読めなかった・なかった記録は、最後に読めた固定と比べる。
- 照合は、記録に残した設定の写しと違う設定で開くと `ok: false` にする（設定のパスを書き換える前の写しに向ければ、照合をすり抜けられたため）。食い違いを受け入れて照合するには `verify({ allowConfigMismatch: true })` と明示し、結果の `config_mismatch_accepted` に残る。
- 鎖のある記録は、末尾の印を先に読み、その後で本体を開く（読み取りの最中の正当な追記で「壊れた鎖」を固定しないため）。
- anchor の記録自身、その関連のファイル（`<記録>.` で始まるもの）、それを含むフォルダは、大文字と小文字を変えても対象にできない。

**この部品はネットワークに出ない。外部のコマンドも呼ばない。** 外へ送る部分（時刻の証明、Bitcoin への固定、別のリポジトリへの写し）は作っていない。外から来た証拠を、固定の値に結び付けて記録する口だけがある。証拠の中身は検証しない。

**検出できること・できないこと。** 攻撃ごとに試験で確かめた。

| 攻撃 | 固定の記録が手元だけにある | 外部が固定の値を持っている |
|---|---|---|
| 鎖のある記録の途中を書き換え、鎖と末尾の印を作り直す | 検出する | 検出する |
| 鎖のない記録（承認、裁定、チェックポイント）の行の書き換え・削除 | 検出する | 検出する |
| 切り詰め、行の抜き取り・入れ替え、1 バイトの変更 | 検出する | 検出する |
| 記録のファイルの削除、差し替え、記号リンクへの差し替え | 検出する | 検出する |
| 判定のファイルの書き換え・削除（足すのは正当） | 検出する | 検出する |
| 固定の記録の行を消す、書き換える | 検出する | 検出する |
| 固定の記録の最後の行を、末尾の印ごと削る | **検出できない** | 検出する |
| 元の記録と固定の記録と末尾の印を、全部作り直す | **検出できない** | 検出する |

下の 2 行が、外への固定が要る理由である。手元だけでは、固定の記録そのものを作り直す書き換えを検出できない。外部が持つ値と突き合わせる口（照合に、外部の値を渡す）は用意した。その値が本物かは、この部品では確かめない。

どの場合も防げないものがある。固定より後の追記、固定の前の書き換え、固定そのものを止めること、最初から偽の記録を固定すること、である。

## 5. 保証できないこと

### 5.1 すべての部品に共通

- **行為者が本物であることは保証しない。** 記録に書く行為者（役割、種類、系統）は、呼び出し側の申告である。行政がこの関数を直接呼べる配置では、オーナーを名乗るだけで採用できる。本物であることは、記録を保護領域に置き、オーナー側のプロセスだけが書く配置で強制する前提で、その配線はしていない。
- **記録の不変性は保証しない。** 記録のファイルと、末尾を固定するファイルを一緒に差し替えられる者（オーナーの権限）の書き換えは検出しない。規則に合う偽の行を作ることもできる。外部への固定はしていない（SPEC §10・§12 と同じ）。
- **宣言から Kernel が動く配線はない。** 編成案や領域パックを検査しても、起動の窓口や裁判所はそれを読まない。

### 5.2 部品ごと

| 部品 | 保証できないこと |
|---|---|
| 権限の差分 | 見るのは権限の表の宣言だけ。フックや裁判所のスクリプトの変更は見ない。説明文の意味は読まない。表の宣言と実装が合っているかは、適合性テストが別に確かめる |
| 改善提案 | 提案者の系統と id は申告で、オーナーが承認した編成の行為者の一覧とは照合しない（系統の要求は、承認した司法の系統で数えるので、この申告に依らない）。系統の要求を解く理由は、中身を確かめない。評価の数は評価者の申告で、試験を再実行しない。対象のパスと変更の種類は提案者の宣言で、中身との一致を確かめない。対象も中身も変えて出し直した提案は、同じ提案と見分けられない。差し戻しの引き継ぎは、同じファイルに触れる別の提案を巻き込む（オーナーの解除が出口）。記録の中で最初の法律の採用は、起点がなければ確かめられず、印を残すだけ |
| 経験 | 出どころの参照が実在するかは確かめない（差し込み口だけある）。命令らしい文の検出と伏せ字は文字列の照合で、言い換えや未知の形は通る。空白を含むパスの後半は伏せ残しうる。生の本文は記録に残る。役割は語彙の表にある名前だけが使える。帰納した経験の範囲は、元の反省より広げられる（採用のときにオーナーが見る前提） |
| グラフ | 着手の組は最初の 1 組だけを返す。依存が統合済みでも、成果物の衝突は見ない。角かっこを含むファイル名は範囲に書けない。大きすぎる組は「確かめられない」として拒む。見た目が似た別の文字と、シンボリックリンクは見分けない |
| 編成案 | 役割がどの権力に属するかの表は、権限の表とエージェントの定義から手で写したもの。系統は申告で、実際に起動したモデルは観測しない。上限の既定値は実運用で確かめていない |
| 実行の状態 | 仕様の指紋、法律の系統、申請の指紋、監査の結果、司法の判定とその重さは、外から来る値で、形と一致しか見ない。判定の重さ（重大かどうか）は、裁判所のスクリプトが判定の記録から機械的に決める前提である。系統の名前は申告のまま。期限はプロセスの生死を見ない。試験のために時計を差し替える入口（`unsafeOpenRunWithClock`）が公開されている。配置するプロセスからは呼ばない。保護を後から足しても、作業中の節が着手の後にした作業は取り消さない（申請の時点で止めるだけ）。申請しないまま作業中にとどまる節は、期限が切れるまで枠と範囲を占める |
| 追跡 | つながりの中身が事実か、成果物が実在するかは確かめない。判定の最新を決める時刻は、書く側の申告である。申請と仕様の結び付きは、夜間の合格の記録に仕様の指紋がないので、直前の承認からの推定である。今の Kernel は統合の SHA を 12 桁しか記録しないので、受け入れの記録がない統合は、呼び出し側が対応表を渡さない限り取り込めない。票の ID の形は開く側の設定で、行に写しを残して食い違いを検出する |
| 外部への固定 | 外から来た証拠の中身（署名、時刻、包含の証明）は検証しない。外部が持つ固定の値が本物かも確かめない。固定の記録そのものが壊れたときの出口はない（退避して、新しく始める）。外へ送る部分は作っていない。`allowConfigMismatch: true` で受け入れた照合は、固定した記録とは違う記録を照合した可能性がある。鎖のある記録の読み直しは 1 回だけで、2 回の読みの両方の最中に追記が続くと、壊れていると誤って固定しうる（誤検出の側）。判定のフォルダの入れ子は 8 段までで、それより深いと固定を拒む（深いフォルダを作れる者は固定を止められる）。入れ子のフォルダの差し替えは、読む前後の i-node の照合で見るだけで、窓はゼロではない |
| 記録の部品（鎖） | 祖先のフォルダの記号リンクは見ない（macOS の `/var` のように、配置で普通にある）。末尾の印と本体の両方を空にした記録は、新しい記録と見分けられない。ほかの道具で整形し直した記録（空白・キーの順序・エスケープの違い）は読めない。本体がハードリンクで書きかけの末尾がある記録は、退避のファイルと復旧の記録を書いた後で止まる（本体は切り詰めない） |
| 橋渡し（`feedbackFromRun`） | 取り出しの行が本物の経験の記録の行であることは確かめない（1 行ずつ規則は確かめるが、記録全体の鎖・版・設定の写しは呼び出し側が確かめる前提）。作業員は、合格しそうな申請の直前に上げたい経験を取り出せば、役に立った評価を付けられる。この評価を経験の昇格の根拠にするときは、オーナーが見る前提 |
| 領域パック | 監査のコマンドが実在するか、決定論的かは確かめない。許可した `npm` と `node` は、`package.json` やスクリプトの中身で任意のコードを動かせる。`--prefix` などの引数は宣言の検査で止めていない。実際の強制は sandbox に依る。司法の入力は名前を固定しただけで、中身が行政の説明でないことは確かめない |

### 5.3 審査で分かった、設計上の割り切り

- 系統と行為者は、今も申告である。司法の役割が別の系統を名乗ることは、語彙の表で拒むようにした。ただし、名乗った系統のモデルが本当に動いているかは、この部品では確かめられない。
- 経験の評価に使う時刻は、2 つの記録（経験と実行の状態）を書いた側の時計である。作業員が経験を本当に読んだか、使ったかは分からない。評価は代理の指標である。
- セキュリティ審査の役割（`codex_security`）は、権限の表にまだない。表に足す改正までは、改善提案の審査者にも、編成にも入れられない。
- オーナー自身の提案は、この記録では採用できない（提案者と採用者を分けるため）。オーナーの変更は、今までどおりの立法の手続きを使う。
- 鎖のロックの引き継ぎは、確かめたフォルダと動かすフォルダを i-node の番号で比べる。番号を再利用するファイルシステム（ext4 など）では、この比較をすり抜ける窓がある（4 回目の審査 L-2）。動かした後の照合で気付いて戻すが、戻すまでの間に 3 つ目のプロセスがロックを取れる。macOS（APFS）は番号を再利用しないので、ここでは確かめられない。Linux へ移すときに確かめる。

## 6. 稼働中の Kernel につなぐときに要ること

設計案の段階 B（[`vgdd-next-architecture.md`](../../docs/design/vgdd-next-architecture.md) §6.2）に当たる。どれも法律の改正で、憲法審査とオーナーの承認が要る。

1. 記録の置き場所を保護領域（Z3）にし、行政から読めず書けないようにする。
2. 行政が提案と経験の候補を置く窓口を作る（起動の窓口と同じ形：決まった名前のファイルを検証して取り込み、元を消す）。フック、設定の原本、権限の表に、この窓口の規則を足す。
3. 評価を、評価者の申告でなく、裁判所の側のプロセスが適合性テストを実際に実行した結果にする。
4. 経験のカウンタの更新を、裁判所が判定を記録するところから呼ぶ。出どころの参照が実在するかを、判定の記録と照合する。
5. 起動の窓口が、起動の前に編成案の検査を呼ぶ。系統は、申告でなく実際に起動した定義から取る。
6. Owner Console に、改善と経験の受け箱を足す。
7. 権限の表に新しい権限を足し、不変条件の候補（設計案 §8）を判例つきで入れる。新しい判例が前の版で落ちることを確かめる。
8. 新しいスクリプトを、実装の指紋の一覧（`kernel-state.mjs` と `run.mjs` の 2 か所）に足す。
